Мелкие исправления в пределах задачи выполняй без отдельного согласования. Смену кода доступа, переписывание истории Git и другие необратимые действия согласовывай явно.

## Бизнес-правила и выводы

- Перед ответом продавцу о рекламе, ценах, запасах или отчётах запусти `node scripts/rules.cjs preflight <тема>`. Выбери подходящую тему из `реклама-озон`, `реклама-вб`, `цены`, `запас`, `отчёт` и `данные`. Для нужного решения сверяй статус, дату, источник и цепочку замен через `rules.cjs find` и `rules.cjs show`.
- Для текущих решений применяй действующие редакции из `ПРАВИЛА.md`, включая условия, которые они явно наследуют. Отменённые правила сохраняй как историю. Проверяй, к каким датам относится исторический расчёт. Например, ЗАП-26 заменяет ЗАП-24, ЗАП-28 заменяет ЗАП-27, ДАН-13 заменяет ДАН-12, РЕК-32 заменяет РЕК-26. Сверяй эти цепочки со сводом перед применением.
- Перед изменением и при проверке расчёта обязательно сверяй реализацию и ожидаемый результат с действующими правилами. Для новинок проверь исключение «спрос известен, до партии мало» и другие условия, которые ЗАП-28 сохраняет из ЗАП-27. Ссылки на отменённые версии в коде или справочниках сверяй с их заменами в `ПРАВИЛА.md`.
- Чтобы заменить правило по подтверждённому решению продавца или замеру, используй `node scripts/rules.cjs revoke <ID> --вместо <новый ID>`. Добавь новую запись с полем `отменяет:`, датой и источником. Выполни `node scripts/rules.cjs check`. Сохраняй прежний текст и причину замены.
- Для анализа цен запускай `price-check.cjs <код 1С> [предельная цена]`. Перед решением по кампании запускай `opyt.cjs brief <код 1С>`. Записывай правки через `opyt.cjs change` со ссылкой на закономерность П-xx по ДАН-06 и сразу учитывай их по ДАН-11. Через неделю проверь `due` и запиши исход через `close`. Для закономерностей используй `pattern` и `confirm`. В опыте проверяй один рычаг. Для Ozon используй `ozon-ozz-detect.cjs` на выгрузке XWAY и `ozon-ad-check.cjs` для сверки «до → после» по снимку. Скрин нужен для разбивки по кампаниям, ставок и бюджетов.
- Называй площадку в заголовках, таблицах и рядом с цифрами. Себестоимость привязывай к коду 1С, она общая для ВБ и Ozon. Используй числа из свежего прогона и явно отмечай оценки и недоступные проверки. Утверждения о рекордах сверяй по всему ряду. Сравнивай закрытые недели пн–вс, для оперативного отчёта сравнивай последний загруженный день с предыдущим. Цены сравнивай внутри сопоставимых сегментов. Вывод об отличии конверсий проверяй по z, органический трафик оценивай по данным. Поправки продавца проверяй как новые факты и объясняй, как они меняют расчёт и вывод.

## Данные и секреты

- Репозиторий публичный. `wb-secure.js` — единственный полный зашифрованный снимок данных в Git (AES-256-GCM, PBKDF2-SHA256, gzip). Документация может содержать фактические бизнес-показатели. Открытые выгрузки и `decrypted/wb-data.js` с `decrypted/wb-reports.js` держи только во временной рабочей области, вне коммитов и публикации.
- Пароли, токены и коды доступа запрещено записывать в файлы, скрипты, документацию, логи, коммиты и артефакты. Не подбирай код и не ищи его в истории.
- **Локальная Windows.** Папка `decrypted/` сохраняется между сессиями. Для согласованной работы со снимком продавец задаёт код в окружении процесса (`VERIFY_CODE`, для скриптов с таким входом — `WB_CODE`). Если переменная отсутствует, попроси продавца задать её локально. Значение запрещено вводить в чат, командную строку, конфигурацию, документацию, логи и Git. Для `decrypt.cjs` и `encrypt.cjs` используй способ передачи из окружения в [CLAUDE.md](CLAUDE.md#рабочий-цикл-с-данными).
- **Временная облачная среда.** Рабочий каталог может исчезнуть по окончании сессии. Когда задаче нужна расшифровка, получай код из защищённого окружения на время запуска. Для чтения документации и кода секрет не нужен.
- В обеих средах после завершения согласованной работы и успешной проверки зашифрованного снимка удали временные расшифрованные файлы и ненужные рабочие копии закрытых выгрузок. Исходные пользовательские отчёты сохраняй независимо от их расположения. При неуспешной проверке сохрани рабочие материалы для сверки. Перед разрешённым коммитом проверь индекс и HEAD на секреты и открытые данные без вывода значений.
- Кабинеты и сервисы подключай только на чтение по ДАН-08. Действия в кабинетах и исправления в 1С выполняет продавец. При согласованной смене кода расшифруй снимок старым, зашифруй новым и сообщи продавцу о прекращении действия старого кода.
- **Перед перешифрованием.** Если `encrypt.cjs` не может прочитать или расшифровать прежний снимок, он пропускает сравнение и может перезаписать `wb-secure.js`. До исправления скрипта запускай перешифрование только после успешной расшифровки текущего снимка его исходным кодом и проверки полей, периодов и контрольных сумм. При смене кода отдельно сверь подготовленные данные с проверенным исходным снимком. Если проверка исходного снимка не подтверждена, остановись до запуска `encrypt.cjs`.
- Расшифруй данные через `decrypt.cjs`, обработай их по тематическому справочнику, сверь контрольные суммы и запусти `encrypt.cjs` с самопроверкой. Сохрани обновлённые `wb-secure.js` и `data-version.json` в рамках разрешённого Git-процесса. Папка `decrypted/` временная. Завершай обновление данных синхронизированным шифрованным снимком. Разбирай каждое предупреждение `data-audit.cjs` и каждую потерю поля, периода или строк. `--allow-drop` применяй только для подтверждённого намеренного удаления.
- Используй общий признак «наш товар» из `scripts/lib/our-codes.cjs`. При перезаписи `wb-reports.js` сохраняй `MODELED_FINANCE` и `BAKED_FUNNEL`. При пересборке в `scripts/ozon-build.cjs` сохраняй `RD.ozon.clusters` и `RD.ozon.clusterHistory` на верхнем уровне `RD.ozon`. В `RD.ozon.meta` сохраняй `terms`, `revBase`, `buyoutWin`, `unitReports`, `adSpend`, `ozzOn` и `orderFee`. Поля, которые добавляют другие скрипты, сохраняй по их фактическим путям.
- После любого обновления остатков запускай `resupply-report.cjs`. Сообщай объём отгрузок всего, на Ozon и на ВБ, сколько позиций нечем закрыть и что срочно. После загрузки склада 1С проверь приход партий и расхождения кодов. После заказов ВБ запускай `model-finance.cjs`. До срока ЦЕНА-13 (01.12.2026) после каждой заливки заказов любой площадки запускай `price-watch.cjs`.
- Понедельничные проверки выполняй по `СТАРТ.md` и разделу «Регулярные дела» в `ЖУРНАЛ.md`. По ДАН-13 загружай «Продажи МП» через `ue-ingest.cjs` без `--costs`, затем `model-finance.cjs`. Подсвети расхождения продавцу и проверь закрытый месяц с допуском 100–150 тыс. ₽ сверх подсвеченных расхождений. Для «О реализации», Китая и производства соблюдай последовательности из `CLAUDE.md` и тематических справочников. План Indeepa перед передачей проверяй `repricer-plan-check.cjs`. Шестизначный код с пометкой «новый товар» заноси через `new-codes.cjs add`. При каждой заливке запускай `new-codes.cjs check`.

## Инварианты кода и расчётов

- `index.html` работает без сборки. Он читает `data-version.json` без кеша и загружает `wb-secure.js?v=…`. Версию снимка и отпечаток сборки формируют скрипты. Статическое подключение снимка и ручное изменение версий запрещены.
- Прибыль Ozon меняй в `calc/ozon-fin.js`, подсорт, полные машины, выкуп для подсорта и раскладку складов — в `calc/resupply.js`. Используй общую реализацию для сайта и скриптов. Новый модуль подключай с `?v=0` для хука. При изменении логики найди все затронутые реализации, включая зависимые расчёты вне списка в `CLAUDE.md`. Синхронизируй их и сверь результат до рубля и штуки. В `resupplyRows` уже объявлена `rest`.
- При изменении логики новинок или влияющих на неё расчётов проверь всю цепочку на одних входах для ВБ и Ozon. Сверь сайт (`index.html`, `srIsNew` и расчёт плана), экспорт Indeepa (`scripts/repricer-plan.cjs`), понедельничный разбор (`scripts/plan-review.cjs`) и независимую проверку (`scripts/repricer-plan-check.cjs`). Сопоставь признак новинки, план и применимость исключений с действующими правилами на каждой площадке.
- Сбрасывай кеши каталога и данных в `hydrateData` и `fdbRefreshCache`. Для себестоимости ВБ на «Всего» сохраняй `wbCostBySku()` и `recWithMp`, для Ozon — `ozCostMap()` с запасным источником `meta.costBySup`.
- Для обеих площадок применяй выкуп с даты замера вперёд. «Выкуплено на сумму» считай как заказано × выкуп. База выручки Ozon — предельная цена без вычета соинвеста. ДРР сравнивай в выкупе с целью Ozon 12% и потолком ВБ 7% по действующим редакциям правил. Оплату за заказ Ozon учитывай по факту отчёта согласно РЕК-23. Месяц Ozon календарный, месяц ВБ по ДАН-13. В `wbMonthOfWeek` передавай исходный день, недели на границе месяца дели по интервалам организации.
- Для складов применяй `whKey()` и ЗАП-19–21. Исключай розничный Евросиб через `whRetailOf()`, когда расчёт начинается с общей суммы `bySup[код].qty`. Для «На вывод» используй `showOut` и `recOutSups()` с отдельной строкой денег скрытых товаров. На «Остатках» применяй ЗАП-06 через `stkRows`.
- Сохраняй объект сортировки `wireSortable` и меняй его поля. Для XLSX в браузере используй `xlsxDownload`. В пяти темах используй токены цвета и `--on-accent`, для тёмной темы — `:root[data-scheme="dark"]`. Для складной справки используй `.howto[data-fold]`.

## Проверка, публикация и завершение

1. Перед публикацией проверь входы по площадкам, датам, полноте и контрольным суммам. Сопоставь результаты с исходными отчётами и контрольными цифрами продавца. Сравни изменённый и прежний расчёт на одних данных, проверь затронутые вкладки и отсутствие побочных изменений в diff. При изменениях парсинга или агрегации сообщи продавцу контрольные суммы для сверки с кабинетом.
2. Для изменений сайта, `calc/` или снимка запусти `sh scripts/check/run-all.sh`. Для полного прогона подготовь расшифрованные данные из проверяемого снимка в `decrypted/`, `VERIFY_CODE` в окружении, Playwright и Chromium. Если Chromium находится вне пути по умолчанию, укажи `PW_CHROME`. Некоторые проверки записывают временные файлы. Например, проверка машин создаёт `scripts/.ft-dump-tmp.cjs`, JSON и XLSX. Храни эти результаты вне коммитов и публикации. Порядок запуска описан в `CLAUDE.md` и `scripts/check/README.md`.

   Текущий `run-all.sh` ищет отдельные строки в выводе дочерних проверок, поэтому код выхода 0 сам по себе не гарантирует прохождение всех проверок. Запусти дочерние проверки отдельно по `scripts/check/README.md` и проверь подробный вывод. Убедись, что все вкладки в режимах ВБ, Ozon и «Всего» заполнены и без ошибок, прибыль Ozon и её контрольные показатели сходятся, а в проверке полных машин нет нарушений, ошибок отдельных тестов и расхождений сайта со скриптом. В новом контейнере перед разрешённым коммитом включи `git config core.hooksPath .githooks`. При сбое или недоступности обязательной проверки обозначь блокер и отложи публикацию.
3. При разрешённой публикации отправляй проверенный коммит только в согласованную ветку. Новый push может отменить текущий деплой. Проверь, что верхний запуск `pages build and deployment` для ветки сайта имеет нужный `head_sha` и статус `completed / success`. Сверь отпечаток `?b=…`. Сообщай об опубликованном результате после подтверждения.
4. По завершении задачи актуализируй `ЖУРНАЛ.md` и `СТАРТ.md` в пределах разрешённого набора файлов. Запиши сделанное, проверки, открытые вопросы и сроки. Для обновления данных укажи площадки и дату покрытия. Долговременные сведения переноси в тематический справочник, подтверждённые решения — в `ПРАВИЛА.md`, исходы опытов — в `ОПЫТ.md`. В памятках ссылайся на дату и название коммита, поскольку история Git уже переписывалась. Итог продавцу формулируй кратко и по-русски.
