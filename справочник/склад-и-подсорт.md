## Оборачиваемость: общее

- **Простая оборачиваемость — ЕДИНАЯ для ВБ и Озона** (`simpleTurnList` + `renderTurnoverSimple`). Старая
  ВБ-модель (`computeTurnover`/`turnoverList`/`exportTurnoverCSV`) в коде, но НЕ вызывается. Источники: **ВБ** —
  `wbStock` · `pending.qty` · `buyoutPct14d` · `containerQty` · `productionStatus`(«На вывод»); **Озон** —
  `ozStock` · `ozTransit` · `ozBuyout`, контейнер — из связанного ВБ-товара.
  Формула оборачиваемости: ср. заказов **7 дн** × выкуп = продаж/день; **«хватит дней» = (остаток + в пути) ÷
  продаж/день** (в пути показан акцентом: «354 **+1000 в пути**», «18 **→ 67**»).
- **Паллеты округляются ВВЕРХ** (`takePallets` в index.html, `take` в resupply-report.cjs — оба `Math.ceil`):
  округление вниз систематически не дотягивало до цели (паллета 108 при нужде 163 → 24 дня вместо 30). Флаг
  `roundUp` у стартовых партий — только пометка «не менее LAUNCH_QTY». Не возвращай `Math.floor`.
- **ПОКРЫТИЕ ВБ = ОСТАТОК НА СКЛАДАХ WB + СВОЙ FBS-ЗАПАС** (27.08.2026, `wbFbsBySup()` в index.html, дубль
  `wbFbsFree` в `resupply-report.cjs`): ВБ продаётся и по FBO, и по FBS с наших складов. **Ловушка: склад Нск-1
  одновременно снабжает Ozon** — один товар нельзя засчитать дважды. В `wbFbsBySup`: сначала потребность Озона
  (с Евросиба, недостача — с Нск-1), в покрытие ВБ — НЕЗАНЯТЫЙ Нск-1 + Москва целиком; Евросиб НЕ входит (по
  FBS с него не торгуют), Клин тоже. В подсорте — по фактической раскладке (`whMsk + max(0, whNsk1 − usedNsk1)`,
  с 21.09 `wbFbsFree = mskFree + nsk1Free`, см. «ПОСТАВКИ НА ВБ FBO ВЕРНУЛИСЬ»). Кеш `_wbFbsCache` сбрасывается
  рядом с `_buyoutWin`.
- **ПОКРЫТИЕ ОЗОНА = только то, что уже на площадке или официально едет на неё.** Товар на СВОИХ складах в
  покрытие НЕ входит (просьба продавца: «хватит дней» от неотгруженной партии сбивало). **ВБ** — остаток на
  складах WB + назначенное на ВБ (журнал `shipments` и РВБ Клин); **Озон** — остаток + `ozTransit` (заявки и
  партии в пути, которые показывает сам Озон; с поправкой на виртуальные склады, см. подсорт).
  Не возвращай `pending.qty` / `ozIncoming` в `covered`.
- **Данные о своём складе при этом СОХРАНЕНЫ**: `catalog[].pending.qty` (ВБ) и `ozon.catalog[].ozIncoming`
  (Озон) пишет **`update-transit.cjs`** из файла «на оптовых» (вкладки `вб` / `озон` / `в пути` / `в пути 2`;
  ВБ = `вб.Итог` + `в пути.Кол-во вб` + `в пути 2.кол-во вб`, Озон — своими колонками; ключ — арт. поставщика =
  WB `supplierCode` = Озон `sku`; файл — полный список едущего, старое `pending` очищается). Нужны для
  «куда и сколько отгрузить», а не для дозаказа.
  **Дозаказ** (`TURN_MIN_DAYS=130`, `TURN_COVER_DAYS=180`): покрытия < 130 дн → партия = **6 мес продаж** =
  `ceil(продаж/день × 180)`, **округляется ВВЕРХ до контейнера** (остаток НЕ вычитаем). Статус: ≥130 «Норма»;
  <130 «Пора дозаказать» (бейдж «Дозаказ»); продажи есть, покрытия нет — «Критично»; продаж нет — «Нет продаж».
  Выкуп — замер по площадке (см. выше), фолбэк `buyoutPct14d`/окно.
  Колонки: Остаток(ВБ/Ozon) · Заказов/дн(7д) · %выкупа · Продаж/дн · Хватит,дн · Дозаказать(+конт.) ·
  Заказать(через N дн) · Статус тов. · Статус. У Озона под остатком «+N в пути»; у ВБ — только склад WB.
  Селектор «Скорость» скрыт (фикс. окно 7 дн); на «Всего» — подсказка выбрать площадку.
- **Производственный статус — СПРАВОЧНЫЙ, на расчёт НЕ влияет** (`prodStatus(sku)` → колонка «Статус тов.»,
  бейдж `pStatusBadge`, фильтр по колонке `pStatus`, ранг `PSTATUS_RANK`): дозаказ и закуп считаются для всех
  видимых товаров, выводимый с остатком получает цель по темпу, решение — за продавцом. Раньше по «На вывод»
  ставился `status="discontinued"` и дозаказ обнулялся —
  **не возвращай это**.
  **ИСКЛЮЧЕНИЕ — «Подсорт со склада»**: товары «На вывод» из подсорта выкинуты, **НО если он лежит на СВОЁМ
  складе, он остаётся** (26.08: «если где-то есть остаток — пока считай, надо быстрее распродать»). Условие:
  `st[s] && !(warehouse.bySup[s].qty>0)`.

    `№ · Код · Артикул · Номенклатура · Количество · Срок изготовления · Срок прихода`, колонки ПО ИМЕНИ, даты
    текстом и числом Excel; «Код» — код 1С с пробелами и запятыми. **НЕ путай с `update-warehouse.cjs order`**:
    тот ПЕРЕЗАПИСЫВАЕТ `inbound.order` целиком (обновление ОДНОЙ партии).
  · **В файле только ОДНА дата — «Срок прихода», и это приход НА СКЛАД ПРОДАВЦА (`eta`).** `etaSale` ставится
    автоматом как `eta + 31 день` (скрипт громко пишет). Другой срок — `set-eta.cjs <ключ> --sale <дата>`
    (`set-eta.cjs` принимает ЛЮБОЙ ключ партии, не только `china`/`order`).
  · **ОБЩИЕ КОДЫ МЕЖДУ ПАРТИЯМИ — ЭТО НОРМА** (количества разные). Скрипт печатает их: если это исправленная
    версия старой партии, а не дополнительная, старую убрать `drop`, иначе штуки задвоятся.
  · В «Разборе товара» партии — КАЖДАЯ СВОЕЙ СТРОКОЙ со своим сроком; в «Запасе и темпе» горизонт по БЛИЖАЙШЕЙ
    партии, остальное — в `alsoQty`.
- **`REAL_DATA.shipments` — журнал отгрузок НА ВБ** `[{id,mp:'wb',sup,sku,qty,left,date,arrived[]}]`: Озон
  показывает поставку официально, а **ВБ путь от отправки до приёмки не показывает вообще**. Продавец сообщает
  сам — **`wb-shipment.cjs add "512190=300, 487175=1200" [дата]`** (ещё `list` / `close <id> [кол-во]` /
  `drop <id>`), отгрузка считается «в пути на ВБ» в подсорте. **Закрывается АВТОМАТИЧЕСКИ в
  `update-wb-stock.cjs`: если остаток по этому коду 1С вырос — значит поставка принята** (продажи остаток только
  уменьшают). Самые старые первыми, не больше роста; скрипт печатает, что закрыл.
- **Вид «По месяцам»** на «Оборачиваемости» (сегмент `#turnViewSeg`, состояние `turnView`): история заказов
  *артикул × месяц* (`monthlyOrders` + `renderTurnMonths`) — окно 7 дн врёт (у новинок нули в старых месяцах,
  ноль в ауте не значит «не покупают»), продавец смотрит пики сам. Пиковый месяц подсвечен, заливка — внутри
  товара, «Ср/мес» **только по месяцам с продажами**, неполные помечены `*`. **Выкуп здесь фиксированный
  `TURN_PEAK_BUYOUT=0.85`** (свой % на истории с нулями не показателен) → «Продаж/дн в пик». Суммы ₽ НЕ
  показываем (деньги в `orderSeries.money` только с середины июля). Выгрузка переключается вместе с видом
  (`exportTurnMonthsCSV`).
- **Виды «Закуп: по пику» / «Закуп: по среднему»** (`purchaseRows(base)` + `renderTurnPurchase`): закуп от истории,
  а не от 7 дней. **Декабрь исключён** из обеих баз (распродажный). Месяцы сравниваются по **среднедневному
  темпу**, а не по сумме (иначе неполный текущий месяц никогда не станет пиком). «Среднее» — по месяцам С
  продажами. Формула: `продаж/дн = темп базы × 0.85` → `нужно = ceil(продаж/дн × 180)` →
  `к закупу = max(0, нужно − «есть»)`, вверх до контейнера. **«Есть сейчас» в закупе = ВСЯ ТРУБА**: остаток на
  площадке + в пути + свой склад (`warehouse`) + Китай (`inbound.china`) + заказано производству
  (`inbound.order` и прочие партии) — иначе заказ на фабрику двоил бы едущее. В «Дозаказе» — только покрытие
  площадки. **Склад/Китай/заказано — ОБЩИЕ для ВБ и Озона** (ключ — код 1С), в каждой выгрузке вычтены
  целиком, поэтому складывать файлы ВБ и Озона нельзя (написано на листе «Как считается»). Выгрузка —
  `exportPurchaseCSV`.
- **Вид «Разбор товара»** (`turnView="item"`, `itemAnalysis` + `renderTurnItem` + `itemDayChart`, выгрузка
  `exportItemXLSX`): «в проформе кода X — 4650 шт, хватит на полгода?». Экран одного кода 1С по ОБЕИМ площадкам
  (товар один, витрины две), поэтому **на переключатель ВБ/Озон не реагирует** и рисуется в `renderTurnoverTab`
  ДО проверок площадки; таблица (`#turnTableCard`) и её фильтры прячутся. Ввод: `#itemQ` код/артикул/название,
  `#itemQty` количество, `#itemMonths` горизонт; при нескольких совпадениях — чипы выбора. Ничего своего не
  изобретает: заказы — `orderSeries`/`ozon.orderSeries`, выкуп — общий `buyoutOf`, остатки — поля подсорта.
  · **ДЕТЕКТ АУТОВ — главное, чего нет в остальных видах**: дни аута идут нулями и занижают средний темп. Дни с
    нулём заказов при живом прежнем темпе — эпизоды (`itemOutEpisodes`), рядом темп ДО и ПОСЛЕ
    (`before`/`after`/`recovery`). Темп не вернулся — карточка потеряла позиции, планировать по доаутному
    (`preRate`). Показы из воронки рядом — подтверждение причины (выпал из выдачи).
  · **ТРИ ПОРОГА, БЕЗ КОТОРЫХ БЛОК КРИЧИТ ВОЛКАМИ**: эпизод открывается при темпе от `ITEM_OUT_MIN_RATE=2`/дн;
    **значимый** (`e.material`, только такие показываются) — не старше `ITEM_OUT_RECENT=45` дней, с потерей от
    `ITEM_OUT_MIN_LOST=8` заказов и прежним темпом от 3/дн; `preRate` — только по провалу не старше 30 дней.
  · **«ПРОВАЛ» И «ТОВАР НЕ ПРОДАЁТСЯ» — РАЗНЫЕ СОСТОЯНИЯ** (`ITEM_OUT_MAX_DAYS=30`): нули длиннее месяца — вывод
    из продажи, а не аут; вместо провала печатается «Продаж нет уже N дней» (`silentDays`/`lastSale`).
  · **РАЗРЫВ ДО ПАРТИИ**: «хватит до» сравнивается с `etaSale` ближайшей партии (выход В ПРОДАЖУ) — правильный
    объём не спасает, если встаёт в продажу позже, чем кончается остаток.
  · **ФИЛЬТР «НА ВЫВОД» СЮДА НЕ ДЕЙСТВУЕТ** (см. `showOut`) — код вводят руками.
  · **ПАНЕЛЬ ВВОДА `#turnItemCtl` ПРЯЧЕТСЯ ЧЕРЕЗ `hidden`, И ЭТОГО МАЛО**: `.itm-ctl{display:flex}` сильнее
    браузерного `[hidden]{display:none}`. Держи правило `.itm-ctl[hidden]{display:none}` — без него баг вернётся.
    Показ/скрытие — в `renderTurnoverTab` ДО проверки `if(!RD)`. Поля — `.itm-f`/`.itm-in` с подписями, а не голые
    `<input>` (стили `.toolbar` привязаны к самому классу, вне его — белые прямоугольники на тёмной теме).
  · **ПАЛЛЕТА И КОНТЕЙНЕР — РАЗНЫЕ ЧИСЛА, НЕ ПУТАЙ**:
    `pallets.bySup[код]` = `{wb,oz}` — штук на ПАЛЛЕТЕ (у площадок разное); `catalog[].containerQty` — размер
    КОНТЕЙНЕРА, кратность заказа на фабрику (на порядок больше). Печатаются оба своими именами; при введённом
    количестве считается объём партии в паллетах и машинах — для проформы это не мелочь.
  · **«Есть сейчас» = площадки + свой склад целиком**; `ozIncoming`/Китай/заказанное — нижним блоком, в «хватит»
    НЕ входят.
  · Инварианты (прогон по всем кодам): «Есть сейчас» = сумма строк трубы = `onSite+atSeller`;
    `хватит дней × продаж/дн = запас`; `продаж/дн = зак.ВБ×выкуп.ВБ + зак.Озон×выкуп.Озон`; внутри эпизода заказов 0.
- **Фильтры/сортировка работают во ВСЕХ видах «Оборачиваемости»** (дозаказ · по месяцам · оба закупа · подсорт).
  «Разбор товара» — нет: таблицы там нет, `renderTurnoverSimple` отдаёт его в `renderTurnItem()` первой строкой.
  Механика: `turnBaseRows()` — строки вида, `turnColDefs()` — колонки ЭТОГО вида (у подсорта и под площадку),
  `turnFilteredRows()` — поиск + категории + список товаров + колоночные фильтры. Селекты категорий/товаров
  заполняются в `renderTurnoverTab` ДО ранних выходов. `renderTurnoverSimple()` в начале делегирует подсорт в
  `renderTurnResupply()` (панель фильтра вызывает именно её).
- **Фильтры по колонкам (Excel-стиль)** — кнопка-воронка в шапке (`.col-filter`, `thSortF()`): панель
  `.colfilter-panel` (стили `.uisel-panel`) со списком **значений колонки** (с подсчётом строк, поиск при >12
  значений). **Фильтры комбинируются логическим И** по колонкам. Состояние — `turnColFilters{ключ:Set значений}`
  (пусто = без фильтра), логика — `turnColDefs()` (`val(r)` — каноничное значение, `sortVal(v)` — для сортировки
  списка), отбор — `turnFilteredRows(all,exceptKey)` (`exceptKey` даёт «контекстные» списки как в Excel). Панель —
  отдельный `position:fixed` div в `<body>` (не режется `overflow`), одна за раз (`_colFilterKey`), закрывается по
  клику вне/Esc/скроллу. Клик по воронке не сортирует (`wireSortable` пропускает `.col-filter`). **Старый
  тулбар-селект статусов удалён** — статус теперь колоночный фильтр. При смене площадки `applyMpData` сбрасывает
  `turnColFilters`. **Выгрузка (`exportTurnoverCSV`, отдаёт .xlsx) идёт строго по текущим фильтрам+сортировке**
  (что видишь — то и качаешь), с ИТОГО по дозаказу; кнопка «Скачать Excel».
