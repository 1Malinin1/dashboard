## Офлайн-скрипты (`scripts/`)

Перед первым запуском: `cd scripts && npm install` (нужен только пакет `xlsx`).

Типовой цикл обслуживания данных:

```
node scripts/decrypt.cjs <код>              # → decrypted/wb-data.js + wb-reports.js
# ...правите decrypted/ через один из скриптов ниже, или руками...
node scripts/encrypt.cjs <код>              # decrypted/*.js → wb-secure.js
node scripts/stamp-build.cjs                # ОБЯЗАТЕЛЬНО, если менял index.html
git add wb-secure.js && git commit && git push
```

- **`stamp-build.cjs`** — пишет в `data-version.json` отпечаток `index.html` (без него правка кода доезжает
  до продавца только с протуханием кеша Pages, до 10 минут). **Руками запускать не нужно — это делает
  git-хук** `.githooks/pre-commit` (когда в коммит попадает `index.html`, сам добавляет `data-version.json`).
  **В НОВОЙ СЕССИИ включи хук одной командой:** `git config core.hooksPath .githooks` — конфиг git'а не
  переживает пересоздание контейнера.
- **`decrypt.cjs <код>`** — `wb-secure.js` → `decrypted/wb-data.js` + `wb-reports.js`.
- **`encrypt.cjs <код>`** — обратно, `decrypted/*.js` → `wb-secure.js` (с самопроверкой roundtrip).
- **`ingest-finance.cjs файл1.xlsx файл2.xlsx ...`** — отчёты «О реализации» и/или «История затрат»
  (тип определяется сам) → построчно в `decrypted/acc-finance.json` / `acc-ads.json` с дедупом по
  отпечатку строки (`rowHash`, идентичен воркеру на сайте). Накопитель не обнуляется; нужен
  расшифрованный `decrypted/wb-data.js`.
- **`bake-snapshot.cjs "новая подпись периода"`** — сливает накопитель в `decrypted/wb-reports.js`:
  новые даты перекрывают старые, остальные сохраняются (недели складываются). **Печатает контрольные
  суммы — сверяй их с личным кабинетом WB перед encrypt/push.** **Переносит `BAKED_FUNNEL` из старого
  снимка как есть** (её печёт `bake-funnel.cjs`; без переноса пропадала вкладка «Товар»). Отбрасывает
  полностью пустые агрегаты — иначе нулевая строка создаёт фантомную дату начала истории.
- **Строки без даты продажи** (прежде всего «Возмещение издержек», у них пусты ВСЕ колонки с датами):
  `aggregateFinanceRows` **размазывает** их по дням того же артикула пропорционально выручке дня (остаток —
  последнему дню, сумма сходится до копейки). Падая целиком на последний день, они проваливали «Прибыль
  по дням». Не возвращай `r.date || maxDate`.
- **ЛЮБОЙ СКРИПТ, ПЕРЕПИСЫВАЮЩИЙ `decrypted/wb-reports.js`, ОБЯЗАН ПЕРЕНОСИТЬ `MODELED_FINANCE`**
  (инцидент 01.09.2026: заливка одной воронки стёрла оценку финансов, «Главная» схлопнулась с 9 недель до 5).
  Перенос есть в `bake-funnel.cjs`, `bake-snapshot.cjs` и `wb-drop-day.cjs`; восстанавливается прогоном
  `model-finance.cjs`, а заметить пропажу можно только по числу недель.
- **`bake-funnel.cjs <день1.xlsx> …`** — запекает **воронку продаж** (подённый отчёт WB «Воронка продаж»)
  в `BAKED_FUNNEL` внутри `decrypted/wb-reports.js`. Те же подённые файлы, что у `wb-extend-orders`/
  `ingest`, но ВСЕ ступени + суммы + остатки. Колонки **по имени** через `indexOf` (индексы «плывут»
  между версиями отчёта; воркер в index.html до сих пор на старых фикс-индексах). Даты из файлов
  перекрывают те же дни; печатает контрольные суммы. Дальше `encrypt.cjs`. Формат записи:
  `{id:дата_sku, date, sku, name, category, impressions, cardViews, addCart, addFav,
  ordersQty, buyoutQty, cancelQty, ordersSum, buyoutSum, cancelSum, wbStock, ownStock}`.
- **`add-catalog-cards.cjs <файл.xlsx> [лист] [--apply]`** — ДОБАВЛЯЕТ новые карточки в каталог ВБ
  (`update-catalog-meta.cjs` только обновляет существующие, неизвестные кладёт в «нет в каталоге»).
  · **КОД 1С ОБЯЗАТЕЛЕН, строка без него НЕ ДОБАВЛЯЕТСЯ.** `supplierCode` — единственная связка со всем
    остальным: артикул Озона = код 1С, склад (`warehouse.bySup`), паллеты, «в пути», режим «Всего», ключ
    строки ПОДСОРТА. Пустые коды схлопнулись бы в один ключ и перемешали товары. Такие строки печатаются списком.
  · По умолчанию СУХОЙ ПРОГОН, запись только с `--apply`.
  · Колонки по имени: «Артикул ВБ» + «Код 1С» (обязательные), «Наименование», «Категория», «Код фабрики»,
    «Статус», «Контейнер», «Себестоимость». Статус по умолчанию «Новинка» (не «На вывод» — иначе карточка
    сразу спрячется по флагу `showOut`).
  · `buyoutPct14d` ставится `null`, а НЕ 0 (ноль = «0% выкупа» и обнулил бы расчёты). `costHistory`
    заводится только вместе с ценой, первая запись всегда `from:null`.
  · **НОЛЬ В СЕБЕСТОИМОСТИ И КРАТНОСТИ ЧИТАЕТСЯ КАК «НЕ ЗАПОЛНЕНО»** (`numPos`, 21.09.2026): продавец
    заполняет файл частями и оставляет 0 в пустых клетках. Ноль ценой = «товар бесплатный», карточка молча
    бесконечно прибыльна; кратность 0 ломает округление дозаказа до контейнера.
  · Дальше: `update-ad-tags.cjs` (склейки новым карточкам) → `encrypt.cjs`.
- **`update-catalog-meta.cjs справочник.xlsx [лист]`** — справочные поля каталога ВБ из рабочего файла
  (колонки по имени: «Артикул Wb» · «код поставщика» · «код фабрики» · «Статус»): `factoryCode` и
  `productionStatus` (регистр нормализуется: «на вывод» → «На вывод»). `supplierCode` **не
  перезаписывается**, только сверяется и проставляется если пуст — тихая правка порвала бы связку
  с Озоном. Печатает новое / изменённое / чего нет в файле. Дальше `encrypt.cjs`.
- **ОСТАТКИ ВБ — ТРИ ФОРМАТА, и ВЕРЕН ТОЛЬКО ОДИН.** `update-wb-stock.cjs` читает «Всего находится на
  складах» (полный отчёт ВБ), «Склад WB РФ» (короткий) и «Текущий остаток товара» (выгрузка XWAY, когда
  ВБ виснет). **Годится только полный отчёт с колонкой «Всего находится на складах»** — проси именно его.
  · **XWAY = FBO + FBS** (разница с отчётом ВБ совпала с новосибирским складом код в код): FBS уже посчитан
    в `REAL_DATA.warehouse`, поэтому XWAY как `wbStock` ЗАДВАИВАЕТ товар — покрытие ВБ раздувается,
    подсорт занижается. Скрипт печатает предупреждение при XWAY-формате.
  · **СКЛАДЫ ВБ СГОРЕЛИ — БЕРЁМ ТОЛЬКО «Склад WB РФ», «Всего находится» НЕ БЕРЁМ** (27.08.2026).
    `«Всего находится» = «Склад WB РФ» + «Склад WB СГТ РФ» + именные склады` (Коледино, Электросталь, …)
    построчно; именные склады сгорели, их цифры — фантом, живой остаток — «Склад WB РФ» (подтвердил
    продавец). Рост «Всего» на величину `catalog.pending` оказался фантомом, а не приёмкой — не принимай
    такое совпадение за доказательство прихода. Приоритет колонок жёсткий: `iRF → iAll → iXway`; при
    обеих колонках печатается, сколько вышло бы по «Всего» (`skippedAll`), без «Склад WB РФ» —
    предупреждение (`onlyAll`). **Не возвращай приоритет «Всего находится».**
  · **`catalog.pending` после этого под вопросом**: числится «в пути на ВБ» по файлу «на оптовых», а в
    остатках его нет. На подсорт/дозаказ не влияет (покрытие ВБ = только `wbStock`), но в ЗАКУПЕ «есть
    сейчас» его учитывает. Проси свежий файл «на оптовых» и перезаливай `update-transit.cjs`.
- **`update-cost.cjs себестоимость.xlsx [дата-с]`** — себестоимость. Ключ по имени колонки
  («Код»/«код поставщика»/«артикул wb»), сопоставляется сначала с `supplierCode` (код 1С), потом с артикулом
  ВБ; цену получают все артикулы кода. Числа и в «озоновском» формате («1,015.09» = 1015.09). **Второй
  аргумент — дата, с которой действует новая цена**: старая уезжает в `costHistory` (см. ниже); без даты
  цена перезаписывается на всю историю. Печатает новое / изменённое.
- **`set-prod-status.cjs "<В работе|Новинка|На вывод>" <коды|--file файл> [--except коды]`** —
  `productionStatus` пачкой («всё отсюда, кроме этих шести, — на вывод»). `list` — сводка. Код 1С
  индексируется и с пробелами, и без них.
- **`missing-pallets-report.cjs [--all]`** — «паллеты-заполнить.xlsx»: товары без вместимости паллеты по
  важности (сверху — что надо везти сейчас и есть на складе). «На вывод» пропускаются (`--all` вернёт).
  Нужен запущенный локальный сервер: цифры подсорта берутся из дашборда.
- **`missing-cost-report.cjs`** — `decrypted/себестоимость-заполнить.xlsx` (товары без цены по продажам).
- **ДАТА ДНЯ У ПОДЁННЫХ ФАЙЛОВ — ДВА ИСТОЧНИКА** (`wb-extend-orders.cjs` и `bake-funnel.cjs`,
  держи синхронно). Обычно — лист «Общая информация»; у того же дня в раскладке СВОДНОГО отчёта (один лист
  «Товары», колонки «… (предыдущий период)») его нет — тогда дата из имени файла (начало и конец, ДДММГГГГ)
  и ТОЛЬКО если они совпадают: отчёт за диапазон раскидать по дням нельзя, нужен `--date ГГГГ-ММ-ДД`.
  Колонки в обеих раскладках — ПО ИМЕНИ («Заказали товаров, шт», «Заказали на сумму, ₽» …).
- **КОЛОНКА «(ПРЕДЫДУЩИЙ ПЕРИОД)» — ХОРОШАЯ ПРОВЕРКА СЦЕПКИ ДНЕЙ, НО РЯД ПО НЕЙ НЕ ПРАВИМ.** Она есть
  У КАЖДОГО АРТИКУЛА (проверено 30.09.2026), то есть перезалить прошлый день технически можно, но **день
  дозревает**: поздние заказы доезжают после утренней выгрузки (~0,5%), и патч закрепил бы ту же
  недозревшую цифру, превратив каждую заливку в переписывание вчера. Расхождение печатаем продавцу, ряд
  правим только свежей подённой выгрузкой за сам этот день.
- **`wb-extend-orders.cjs [--date ГГГГ-ММ-ДД] <день1.xlsx> …`** — продлевает `REAL_DATA.orderSeries`
  заказами ВБ (лист «Товары» → «Заказали товаров, шт» кол.19, ключ «Артикул WB»; дата из «Общей
  информации»), копит **₽ по дням** в `orderSeries.money` (кол.31 «Заказали на сумму, ₽», кол.34 «Выкупили
  на сумму, ₽»). Дни из файлов перезаписываются, прочие сохраняются; ряды всех sku одной длины с `dates`.
- **`wb-drop-day.cjs <ГГГГ-ММ-ДД>`** — вырезает ОДИН день из данных ВБ: `orderSeries` (dates + все ряды
  `bySku` + `money`) и `BAKED_FUNNEL`. Нужен, когда прислали отчёт за СЕГОДНЯ: неполный день роняет окно
  «последние 7 дней» в подсорте. Индекс вырезается из ВСЕХ рядов, длина проверяется, при расхождении снимок
  не пишется. **Файл отчётов переписывается целиком — в ТОЙ ЖЕ форме, что у `bake-funnel.cjs`**
  (со служебными `BAKED_AT`, `*_ROWS`): без них `encrypt.cjs` падает с ReferenceError.
- **`opyt.cjs`** — журнал правок кампаний и закономерностей (`ОПЫТ.md`). С 19.10.2026 в обеих таблицах колонка
  **«площадка»** (Ozon / ВБ / обе); колонки читаются ПО ЗАГОЛОВКУ (`table`/`COLS`) — так же, как `OPYT_COLS`/`opytMap`
  в index.html (блок «Гипотезы и опыты» на «Рекламе»), ДЕРЖИ СИНХРОННО. Формы: `change "<площадка>|<код>|<что>|<база>|
  <дата проверки>"`, `pattern "<площадка>|<текст>|<эффект>|<где>"`, `brief <код> [площадка]`, `due`, `close <ID> "<исход>"`,
  `confirm <ID>`, `add-mp-column` (добавить колонку в старый файл; повторный запуск безопасен). Старая форма без
  площадки пишет Ozon с предупреждением.
- **`xlsx-xml-reader.cjs`** — резервный читатель .xlsx напрямую по XML (см. ниже, «когда SheetJS виснет»).
- **`lib/parse-wb.cjs`** — общая логика (num/rowHash/парсеры/агрегация). **Если меняешь формулу «Итого
  к оплате» или набор колонок в воркере `index.html` — обновляй и здесь**, иначе отпечатки строк
  расходятся и офлайн-дедуп сломается.

## ПРАВИЛО: продавец присылает 6-значный код — это новый товар (`scripts/new-codes.cjs`)

**Договорённость 12.10.2026, дословно:** «я тебе буду кидать 6-значный код с пометкой новый
мой товар, и ты будешь добавлять и на вб и на озон. Схема такая — ты получаешь 6-значный код,
после этого как только я тебе скидываю какой-либо отчёт, ты уже притягиваешь к нему либо
артикул вб либо артикул озон, и эти товары спокойно встраиваются в панель и по ним идут все
возможные расчёты».

**ПОЧЕМУ НУЖНО ХРАНИЛИЩЕ В СНИМКЕ, А НЕ ПАМЯТЬ ЧАТА.** Между кодом и первым отчётом с артикулом
проходят дни, контекст сессии до этого не доживает. Код, названный в переписке и нигде не
записанный, теряется МОЛЧА: товар продаётся, а в дашборде его нет — ни в подсорте, ни в закупе,
ни в прибыли, и заметить это нечем. Поэтому список живёт в `REAL_DATA.meta.newCodes`.

**ЧТО ДЕЛАТЬ:**
1. Получил код → сразу `node scripts/new-codes.cjs add "519333, 519334"` (ничего не спрашивая).
2. **При КАЖДОЙ заливке любых отчётов** → `node scripts/new-codes.cjs check <все файлы>`.
   Скрипт ищет коды во всех листах, вытаскивает рядом стоящие «Артикул WB» / «SKU» / название
   и дописывает их в запись. Это и есть «притягивание артикула» из договорённости.
3. Нашёлся **артикул ВБ** → карточка через `add-catalog-cards.cjs` (код 1С обязателен).
   Нашёлся **только SKU Озона** → `new-codes.cjs oz <код> <ozonSku> --name … --cat … --wbcat …`.
4. Карточка заведена → `new-codes.cjs drop "<код>"`, чтобы список не разрастался.

**`--wbcat` ПРИ ЗАВЕДЕНИИ ТОЛЬКО НА ОЗОНЕ ОБЯЗАТЕЛЕН.** В режиме «Всего» категория берётся как
`wbCategory || category`, и карточка без неё притащит на общую вкладку озоновское название
(«Каталка»), которого в списке категорий ВБ нет — ломается инвариант «чужих категорий на Всего
ноль» и фильтр делит выборку. Берётся из каталога ВБ, если связка есть; иначе задаётся руками.

**ПЕРЕЧЕНЬ ВСЕХ КОДОВ ОТ ПРОДАВЦА СВЕРЯЙ В ОБЕ СТОРОНЫ.** 12.10 он прислал файл из 153 кодов
(«старые и новые»). Полезны обе проверки: каких из них НЕТ у нас (нашёлся 512191 — карточка ВБ
есть, в каталоге не было) и какие есть у нас, но нет в перечне (302 кода — это выведенный
ассортимент, нормально; но 17 из них с живым остатком, и это стоит показать).

**РАСХОЖДЕНИЕ КОДА 1С МЕЖДУ ВБ И КАТАЛОГОМ — НЕ ПРАВИТЬ МОЛЧА.** На 12.10 нашёлся случай:
у карточки ВБ 46008405 артикул продавца в отчётах = **512191**, а в каталоге стоял
`supplierCode` **311115**. `supplierCode` связывает со складом, Озоном и паллетами, поэтому
тихая правка рвёт связки (см. `update-catalog-meta.cjs`, который его намеренно не перезаписывает).
Спросил — продавец ответил: «512191 верный код, раньше товар просто продавался под 311115,
технически это одна и та же карточка просто со смененным артикулом». Заменено во ВСЁМ снимке
(30 вхождений: карточка ВБ, карточка Озона, 13 строк воронки Озона, ряд заказов), статистика
сохранена. **Правило на будущее: при смене артикула переименовывай код ВЕЗДЕ, а не заводи
второй** — иначе история товара расколется на две половины и ни одна не будет полной.

**КАРТОЧКА НА ОЗОНЕ ЕСТЬ, А В СНИМКЕ НЕТ — ЭТО НЕ ПОТЕРЯ ДАННЫХ** (12.10.2026).
`ozon-build.cjs` собирает каталог Озона ТОЛЬКО из заказов и отчёта остатков, поэтому товар,
заведённый на площадке но пока не продававшийся и не отгружавшийся, не попадает в него вовсе.
Единственный источник связки «код 1С → SKU Озона» без продаж — **перечень XWAY** (лист
«Страница 1», колонки «Артикул продавца» + «SKU»). Заводятся пачкой:
`new-codes.cjs oz-bulk <перечень.xlsx> "Страница 1" [--apply]` (сухой прогон по умолчанию,
пропускает уже заведённых и коды без карточки ВБ, кладёт НУЛЕВОЙ ряд `byArt` длиной с `dates`),

## Как передать пользователю недостающие товары / кастомные отчёты

Смотри `missing-cost-report.cjs` как образец: генерируешь `.xlsx` в `decrypted/`
через `XLSX.writeFile`, отдаёшь через инструмент отправки файлов пользователю

обратно — дальше `update-cost.cjs` на результате.

## Ключевые данные/форматы (чтобы не удивляться при отладке)

- **`REAL_DATA.catalog[]`**: `{sku, factoryCode, supplierCode, name, category,
  wbStock, inTransitToWB, ownWarehouseStock, buyoutPct14d, containerQty,
  productionStatus, pending, costPrice, costHistory}`. `costPrice: null` = себестоимость не задана
  (UI предупреждает и даёт вписать вручную/через файл).
- **`costHistory` — история себестоимости** `[{from:null|iso, cost}]` по возрастанию даты. Первая запись
  ВСЕГДА с `from:null` (гарантирует `update-cost.cjs`), иначе `costAt()` не найдёт цену прошлых дат и молча
  пересчитает прошлые недели по текущей. Зачем: новая цена действует **только с даты поставки**, прошлое
  не трогаем. `costAt(sku,date)` — цена на дату (ручной `costOverrides` перекрывает всё), `costOf(sku)` —
  текущая. **Себестоимость проданного — ПОСТРОЧНО по дате строки** в `finAggregate`, `finSeriesByDate` и
  `finAggBySku` (там `cogs` копится сразу, `productPnL` его только берёт). Форвард-расчёты (дозаказ, закуп,
  безубыточность) — `costOf`. Проверка при заливке: cogs за прошлый период до и после — до рубля.
- **`REAL_DATA.orderSeries`**: `{dates:[iso...], bySku:{sku:[qty по дням, той же длины что dates]}},
  money:{iso:{sku:[заказано₽,выкуплено₽]}}}`. Ряды `bySku` строго одной длины с `dates` — при добавлении
  дней продлевай ВСЕ ряды (нулями), иначе графики съедут. `money` — разреженная карта по дням, питает
  «Сумма заказов и выкупа по дням» на «Динамике»; у Озона — `ozon.orderSeries.money`. В UI — хелпер
  `mpMoney()`. **На «Всего» деньги СВОДЯТСЯ по коду товара** (`combinedMoney()`: у ВБ sku → `supplierCode`,
  у Озона артикул и есть код; возвращает `{all,wb,oz}`).
- **`BAKED_FINANCE[]`** — свод по (дата+артикул): `{id,date,sku,name,category,
  qty,returnsQty,revenue,payout,logistics,penalty,storage,reimb,deduction,
  priyomka,loyalty,loyaltyPts}`. `revenue`/`qty`/`returnsQty` — только из строк Продажа/Возврат, остальные
  денежные поля — сырые суммы расходов, не привязанные к продаже.
- **`BAKED_ADS[]`** — `{id,date,sku,spend}` по (дата+артикул) из «Истории затрат», только кампании `18+...`,
  артикул = последние цифры в названии кампании.
- **`BAKED_FUNNEL[]`** — воронка по (дата+sku): `{id,date,sku,name,category,
  impressions,cardViews,addCart,addFav,ordersQty,buyoutQty,cancelQty,ordersSum,buyoutSum,
  cancelSum,wbStock,ownStock}`. Питает «Товар». Живёт в `wb-reports.js` рядом с `BAKED_FINANCE`/`BAKED_ADS`;
  `encrypt/decrypt.cjs` переносят (старый снимок без воронки → `[]`). `fdbRefreshCache` кладёт
  `BAKED_FUNNEL` базовым слоем, загрузки IndexedDB — поверх. `funnelIsBaked`/`funnelHasBaked` — как у
  финансов. **Суммы `ordersSum`/`buyoutSum` воронки сходятся с `orderSeries.money` до рубля** (один
  источник) — хороший чек консистентности.
- **Формула «Итого к оплате»** (сверена на суммах магазина, 99.99%):
  `К перечислению − логистика − штрафы − удержания − хранение − операции приёмки
  − стоимость лояльности − баллы лояльности − возмещение издержек`.
  «Возмещение издержек» — РАСХОД (вычитается), не доход. См. `finHoldings`/`finNet` в index.html.
- **Прибыль** = Итого к оплате − Себестоимость проданного − Реклама.

## Загрузка данных — только через диалог (браузерные дропзоны убраны)

Пользователь грузит все данные **через диалог** (ИИ запекает в снимок), а не через
браузер. Дропзоны на вкладках «Товар» (себестоимость, воронка) и «Финансы» (реализация,
реклама) **удалены** — браузерная загрузка жила только в IndexedDB локально до чистки
кэша и вводила в заблуждение. Функции-обработчики `handleFunnelFiles`/`handleCostFiles`/
`handleFinanceFiles`/`handleAdsFiles` и воркер парсинга **остались в коде, но НЕ
подключены к UI** (мёртвый код) — если понадобится снова, достаточно вернуть дропзону и
обвязку. `renderCostInfo`/`renderAdsHistoryInfo` — с null-guard, безопасны без своих
элементов. **Разные цифры в разных браузерах** = в одном остались локальные данные
(старые IndexedDB-загрузки финансов/рекламы/воронки или ручные правки себестоимости
`costOverrides` в localStorage `wb_cost_overrides_v1`). В строке свежести показывается
ссылка «сбросить локальные данные» (`localDataResetLink()` → `resetLocalData()`: чистит
три стора IndexedDB + costOverrides + reload) — только когда локальные данные есть
(флаги `*HasBaked && !*IsBaked`). После сброса везде — единый зашитый снимок.
**Воронка теперь запекается в снимок** — см. `BAKED_FUNNEL` ниже
(`FUNNEL_CACHE` = зашитый снимок + браузерные загрузки поверх, как у финансов).

## Выкуп, реклама в прибыли и оценка финансов ВБ

- **% ВЫКУПА ДЕЙСТВУЕТ С ДАТЫ ЗАМЕРА И ВПЕРЁД — ПРОШЛОЕ НЕ ТРОГАЕМ** (07.09.2026: «как только я скидываю новый
  и мы его обновляем, старые расчёты ты не трогаешь, а просто конвертируешь заказы в выкуп все последующие»).
  Раньше `model-finance.cjs` применял последнее окно ко ВСЕМУ периоду, и каждый отчёт переписывал прошлые
  недели «из воздуха». Механика: выкупы заносятся ВБ днём ЗАКАЗА, поэтому период, измеренный позже,
  показывает процент выше — свежий процент в старых днях завышает прошлое.
  · **КЛЮЧ — ДАТА ЗАМЕРА (`builtAt`), А НЕ ДАТЫ ОКНА ВНУТРИ ОТЧЁТА** (окно 17–30.08, замеренное 07.09,
    действует с 07.09). Это учёт продавца. Не «чини»
    обратно на разбивку по окнам.
  · `meta.buyoutWin.history[]` — все замеры `{from,to,all,moneyAll,bySku,builtAt}`, ведёт `wb-buyout-window.cjs`.
    **Повторный замер того же окна НЕ перезаписывает запись** — иначе прошлое опять поехало бы.
  · `model-finance.cjs`: `winFor(d)` — ПОСЛЕДНИЙ замер с `builtAt <= d`; дни раньше первого — по нему же.
    `mbFor`/`boFor` — то же для денежного и штучного процента; печатается разбивка «с какой даты какой процент».
  · Ручной `--buyout` перекрывает историю и применяется ко всем дням — только для прикидок.
  · Проверка после правок: два замера дают две полосы дат, граница — дата второго замера.
- **ИСТОЧНИК % ВЫКУПА ВБ — `scripts/wb-buyout-window.cjs`, а НЕ подённая воронка.** Читает **сводный** отчёт
  аналитики за период → `REAL_DATA.meta.buyoutWin`. **ПРАВИЛО ПРОДАВЦА (01.09.2026, файл КАЖДЫЙ ПОНЕДЕЛЬНИК):**
  · окно = **14 дней, пропустив последние 7** (свежая неделя ещё едет);
  · **% выкупа = ВЫКУПЛЕНО ÷ (ВЫКУПЛЕНО + ОТМЕНЕНО)** — «от ЗАКРЫТЫХ заказов», ровно как колонка «Процент
    выкупа» в кабинете ВБ (сверено: `1829 ÷ (1829+577) = 76.0%` при «76» в листе «Фильтры»).
  **ПОЧЕМУ НЕ «÷ ВСЕ ЗАКАЗЫ»**: заказ «в пути» ещё не выкуп и не отмена; старая формула считала их
  невыкупленными и занижала свежее окно. **На зрелом окне обе формулы совпадают** — это снятие смещения, а не
  смена смысла; поэтому порог `MATURE_OPEN_PCT` для ВБ не нужен, «в пути» печатается справочно.
  **Не путать** с «от неотменённых» (`b ÷ (заказано − отменено)`) и с `buyoutPct14d` из каталога.
  **ДЕНЕЖНЫЙ выкуп — на той же базе**: `выкуплено ₽ ÷ (выкуплено ₽ + отменено ₽)`, идёт в `model-finance.cjs`
  (прежние `rb/ro` занижали оценку выручки).
  **МЕРЖ, А НЕ ЗАМЕНА `bySku`**: отчёт бывает отфильтрован по одному предмету (лист «Пушкары», а не «Товары» —
  лист ищется по содержимому); перезапись стёрла бы свой % у остальных (он идёт в ДРР по уровням и потолок
  CPO). Новые значения перекрывают, ненайденные сохраняются; счётчики `bySkuFresh`/`bySkuKept`. Свой % — при
  **10+ ЗАКРЫТЫХ** заказах, иначе общий.
- **РАСХОД НА РЕКЛАМУ — ТРИ ИСТОЧНИКА, И ВСЕ ТРИ ИДУТ В ПРИБЫЛЬ** (`fdbRefreshAdsCache`):
  1) `BAKED_ADS` — «История затрат» ВБ (29.06–02.08, дальше отчёты закрыли); 2) загрузки IndexedDB (легаси);
  3) **`adPerf.parts` — выгрузки XWAY** (`adRowsFromPerf`; добавлено 01.09.2026 — без него прибыль после 02.08
  шла с рекламой 0). Приоритет: «История затрат» > загрузки > XWAY; XWAY — ТОЛЬКО за даты, которых нет в
  первых двух (иначе двойной счёт). **Сумма за период фактическая, разнесение по дням РАВНОМЕРНОЕ**.
  Двойного счёта с оценкой нет: в `MODELED_FINANCE` поля `ads` нет, `FIN_MONEY` рекламы не содержит — она
  всегда из `adAggregate`. Недели без загруженной рекламы завышены — проси выгрузки XWAY за пропущенные дни.
- **`MODELED_FINANCE` — ОЦЕНКА финансов за даты после факта** (`scripts/model-finance.cjs`): отчёты
  «О реализации» закрыты, свежие недели — из заказов: `заказано ₽ × денежный выкуп` → выручка, `× payoutRate` →
  «итого к оплате», минус себестоимость (заказы × выкуп по sku, цена `costAt` на дату) и реклама (`--ads`,
  пропорционально выручке дня). Живёт в `wb-reports.js` рядом с `BAKED_FINANCE`, переносится encrypt/decrypt,
  в `unlock()` → `window.MODELED_FINANCE`.
  **Каждая строка помечена `est:true`, и дашборд обязан об этом говорить:** `fdbRefreshFinanceCache`
  подмешивает оценку только за даты, которых НЕТ в факте, выставляет `financeEstFrom/To`; строка свежести —
  «факт по X, дальше ОЦЕНКА», недели помечены «оценка» (`r.est`). Не давай оценке молча слиться с фактом.
  Денежный выкуп — из `meta.buyoutWin.moneyAll`, а НЕ штучный (чеки выкупленного и заказанного различаются на
  ~12% выручки); его кладёт `wb-buyout-window.cjs`, чтобы прогон не зависел от `--buyout`.
  Пришёл настоящий отчёт за период — `node scripts/model-finance.cjs --clear`. Проверка 24.08: оценка попала
  в то, что недозревший отчёт покажет после дозревания.
- **`REAL_DATA.meta.model` — финансовые коэффициенты, снятые с ФАКТА** (`scripts/calibrate-model.cjs`).
  **Продавцу закрыли доступ к финансовым отчётам 24.08.2026 — новых данных не будет, пересчитать
  коэффициенты не из чего**; сняты один раз с 5 недель (29.06–02.08). Надёжно: `payoutRate` = «итого к оплате»
  ÷ выручка = **62.0%** (структурная величина), `avgTicket`. НЕ надёжно: `soldPerOrdered` (зависит от тренда,
  годится на месяц, не на неделю). `adRate` — решение продавца, а НЕ коэффициент: прогноз обязан брать рекламу
  вводом.
- **% ВЫКУПА — ОКНО «ПРОПУСТИТЬ НЕДЕЛЮ, ВЗЯТЬ ДВЕ»** (24.08, одно правило на обе площадки) — ныне ФОЛБЭК, когда
  нет замера отчётом (у обеих площадок замеры есть). `BUYOUT_HOLD=7`, `BUYOUT_WIN=14`, `BUYOUT_MIN_ORD=10`:
  14 дней, кончающихся за 7 до последней даты воронки; источник — воронка `ordersQty`→`buyoutQty` (у Озона
  «Доставлено»); свой % при 10+ заказах. Хелперы `buyoutFromFunnel`/`buyoutInfo`/`buyoutOf` в index.html,
  дубль в `scripts/resupply-report.cjs` — **держи синхронно**. Кеш `_buyoutWin` сбрасывается
  в `hydrateData` и `fdbRefreshCache`.
  **ПРОВЕРКА ЗРЕЛОСТИ обязательна, и она по ФИЗИКЕ, а не по тренду**: выкуп в снимке заморожен на момент
  выгрузки; признак — день с 20+ заказами и выкупом <15% (такого не бывает). Хоть один такой день → окну не
  верим, берём прежний источник (`buyoutPct14d` у ВБ, `ozBuyout` у Озона), `turnHowTo` пишет, что применилось
  РЕАЛЬНО. Сравнение начала окна с хвостом **не работает** (мёртвые дни бывают в начале). Окно по воронке
  зреет, только если день выгружен ПОЗЖЕ — одна свежая выгрузка за весь период окна.

## Себестоимость

- **ЦЕНА ПРИХОДИТ РАНЬШЕ КАРТОЧКИ — ФОЛБЭК `meta.costBySup`** (13.10.2026). Себестоимость приходит, как только
  распределён контейнер, — ДО появления артикула в отчётах; `update-cost.cjs` такой код не принимает
  («не найдены»). А код, вышедший сначала на ОЗОНЕ (карточки ВБ нет), без цены считался бы с нулевой —
  молча бесконечно прибыльным (тот же капкан, что `numPos` в `add-catalog-cards.cjs`).
  · Кладёт **`new-codes.cjs cost "519333=3358, 519594=173"`** — в `meta.costBySup[код]` и в список ожидания.
    **Ноль ценой не считается** (см. `numPos`).
  · Читают `ozCostMap()` (index.html) и `ozon-finance.cjs` — **держи синхронно**. Каталог ВБ СИЛЬНЕЕ:
    фолбэк — только если в каталоге цены нет.
  · `add-catalog-cards.cjs` при заведении карточки ПОДХВАТЫВАЕТ эту цену (если в файле нет) и УБИРАЕТ запись
    из фолбэка — иначе два источника правды разъедутся при первом `update-cost.cjs`. Зал ожидания, как `newCodes`.
- **Себестоимость ОБЩАЯ для ВБ и Озона.** Ведётся только в `RD.catalog` (ВБ); на Озоне цена подтягивается в
  `rebuildCatalogMaps` через `wbBySup[артикул Озона]` вместе с `costHistory` (`costAt()` на Озоне знает
  историю). `costOf`/`costAt` на обеих площадках дают одно и то же; `update-cost.cjs` обновляет обе сразу,
  отдельного шага для Озона НЕ нужно.

## Файлы репозитория — подробно

| Файл | Что это |
|---|---|
| `index.html` | Весь сайт: стили, разметка, вся JS-логика. Снимок грузится ДИНАМИЧЕСКИ (`loadSnapshot` в конце файла): сначала `data-version.json` без кеша, потом `wb-secure.js?v=<оттуда>`. Руками версию бампить НЕ надо. |
| `data-version.json` | Версия снимка + отпечаток разметки (`{v,period,builtAt,build,stampedAt}`). `encrypt.cjs` **дописывает** сюда `v` (полная перезапись сносила `build`, и самообновление молча выключалось после обычной заливки данных). Крошечный, грузится `cache:"no-store"` — поэтому обновление данных доезжает до браузера даже с закешированным `index.html`. Раньше версия жила в query внутри index.html и залипала вместе с ним: продавец видел «заказы по 3 авг», хотя в репозитории лежало 5-е. Не возвращай статический `<script src="wb-secure.js?v=...">`.<br>**`build`** — sha1 самого `index.html`, ставит `scripts/stamp-build.cjs`. Страница сверяет его со своим адресом `?b=…` и при расхождении ОДИН раз перезагружается по новому адресу — иначе после правок кода продавец ещё минут десять видит старую страницу из кеша Pages. Зациклиться нельзя: после перехода адрес уже содержит нужный build. Плюс `watchBuild` следит за обновлениями У ОТКРЫТОЙ вкладки: сверяет отпечаток при возврате на вкладку (`visibilitychange`/`focus`) и раз в 10 минут — дашборд у продавца сутками висит открытым и сам по себе не перезагружается. |
| `wb-secure.js` | Единственный файл с данными в git. Зашифрован. Формат: `const WB_SECURE = {v,alg,kdf,hash,iter,zip,salt,iv,ct,period}`.   (CLAUDE.md 318 → 25 КБ, запретов потеряно 0).
- **История git ПРОРЕЖЕНА 18.10.2026 по просьбе продавца** («делай»): копии снимка `wb-secure.js` — все за
  последние 2 недели, раньше — по одной на неделю (последняя версия недели); код и памятки — целиком; все
  оставленные снимки перешифрованы НОВЫМ кодом, старый код вычищен из `missing-pallets-report.cjs` во всей
  истории. Хэши коммитов изменились — **не ссылайся на хэши в памятках**, пиши дату и название коммита.
  Повторять прореживание можно только по его просьбе (повод — размер репозитория к 1 ГБ). Метод: `git fetch
  --unshallow` (контейнер клонирует лишь 50 коммитов) → `git bundle` на всякий случай → карта «версия снимка →
  оставленная версия» (выкинутая заменяется последней оставленной НЕ ПОЗЖЕ неё) → `git filter-branch
  --index-filter` с `git update-index --cacheinfo` → проверка: дерево HEAD не изменилось, все снимки открываются
  кодом → `git push --force` на три ветки. Без просьбы историю не трогать.

## Регулярная процедура: еженедельное закрытие недели (продавец грузит отчёт по понедельникам)

Продавец просил: **каждый понедельник после его загрузки — цифры за прошедшую неделю.**
Финансовых отчётов у него больше нет, поэтому неделя закрывается ОЦЕНКОЙ:

```
node scripts/wb-extend-orders.cjs <подённые файлы...>   # заказы (штуки + ₽)
node scripts/bake-funnel.cjs <те же файлы...>           # воронка
node scripts/wb-buyout-window.cjs <сводный отчёт.xlsx>  # % выкупа, если прислал сводный
node scripts/model-finance.cjs --ads <реклама за период>  # оценка финансов (по умолчанию 0)
node scripts/encrypt.cjs <код> && git commit && git push
```

В ответе продавцу за неделю давать: **выручка · итого к оплате · себестоимость · реклама ·
прибыль · маржа**, и обязательно помечать, что это оценка, а не отчёт. Сводный отчёт аналитики продавец присылает
по понедельникам (правило 01.09.2026: окно 14 дней, пропустив последние 7, — см. «Источник % выкупа ВБ»): он и уточняет
`% выкупа` (`wb-buyout-window.cjs`), и служит проверкой модели. Не прислал — спросить (прежнее «раз в 3 недели» снято).

## Регулярная процедура: 15-е число месяца — зафиксировать авто-план (ДАН-04)

При первой заливке, где у площадки есть 15-е число месяца, открыть «Рекомендации» → карточку плана (там уже
расчётный план «+30% к темпу 1–15») и записать её цифры в снимок: `node scripts/set-plan.cjs <ГГГГ-ММ> --wb N --oz N
--auto` → `encrypt.cjs`. Без этого план считается по текущим данным и сдвигается от поздних выгрузок за 1–15, а по
правилу он после 15-го не меняется. Продавцу — одной строкой: план месяца по каждой площадке.

## Регулярная процедура: после любого обновления остатков — пересчитать подсорт

Продавец попросил явно: **после КАЖДОЙ заливки остатков — ВБ, Озона или своего склада —
всегда пересчитывать необходимость подтоварки и сообщать результат.** Не ждать вопроса.

```
node scripts/resupply-report.cjs [дней=30] [строк=15]
```

Скрипт повторяет логику вида «Подсорт со склада» (те же покрытия, тот же приоритет Озону)
и печатает: сколько позиций требуют подсорта, сколько срочных, сколько штук отгрузить на
каждую площадку, чего нечем закрыть и что останется на складе. Его цифры обязаны совпадать
с дашбордом — это заодно проверка, что заливка не сломала расчёт.

В ответе продавцу после обновления остатков давать минимум: **к отгрузке всего / на Озон /
на ВБ · сколько позиций нечем закрыть · что срочное**.
