# XWAY MCP для Wildberries

Продавец подтвердил 24.11.2026 работу всех девяти инструментов в локальном Codex на Windows. Доступ к кабинету ВБ — только на чтение (ДАН-08). Облачное подключение пока не подтверждено. Для Ozon источниками остаются выгрузки XWAY, отчёты Ozon и скриншоты продавца. [Методика Ozon](../СПРАВОЧНИК-ОЗОН.md) · [Учёт рекламы Ozon](озон-учёт.md)

## Подключение и роли

| Параметр | Значение |
|---|---|
| Сервер XWAY | `https://am.xway.ru/api/public/v1/mcp` |
| Транспорт | Streamable HTTP |
| Авторизация | `env_http_headers.Authorization = "XWAY_API_TOKEN"`. Codex берёт значение заголовка из пользовательской переменной Windows, без префикса `Bearer`. |
| Исключения Bebra VPN | `am.xway.ru` и `mcp.mpstats.io` |

XWAY даёт рекламную статистику ВБ и текущие настройки. Dashboard определяет ассортимент и рассчитывает внутреннюю экономику. Codex получает данные, выполняет расчёты и ведёт документацию. ChatGPT служит для обсуждения стратегии и решений. GitHub хранит проект и историю, через него публикуется дашборд. MPSTATS предназначен для оценки рынка, спроса и конкурентов после восстановления доступа. На 24.11.2026 он недоступен.

Значение токена остаётся в пользовательской среде Windows. Закрытые выгрузки, ответы с данными кабинета, ID магазина и секреты держать вне публичного репозитория. При HTTP 401 проверить доступность переменной для процесса Codex и срок действия токена, не выводя значение.

## Как ограничить запрос своим ассортиментом ВБ

1. Начать с актуального снимка Dashboard. Функция `ourCodes(RD).has(код)` проверяет принадлежность по коду, объединяя источники ВБ, Ozon, 1С и реестр новинок. В этом множестве есть товары без карточки ВБ. Соответствие артикулов нужно установить отдельно. [Реализация признака «наш товар»](../scripts/lib/our-codes.cjs)
2. Для нужного кода взять все подтверждённые пары из каталога ВБ (`RD.catalog[].supplierCode` и `sku`). Сверить артикул продавца с `vendor_code`, а артикул ВБ с `list_products.items` → `id` (nmID). Передавать в запрос только подтверждённые артикулы продавца или nmID, в зависимости от метода. Внутренний `id_xway` для запросов не используется.
3. В `list_products` и `get_product_statistics` добавлять `visible=true` к фильтру своих артикулов. Если ожидаемая карточка пропала, проверить ровно её по артикулу без фильтра видимости. Несовпадение кодов, неоднозначную привязку или расхождение видимости сообщить продавцу. Спорные строки оставить вне расчёта. Видимость в XWAY сама по себе не даёт основания расширять ассортимент Dashboard. Если актуальный ассортимент Dashboard недоступен, массовый разбор отложить.
4. Для кампаний передавать только подтверждённые nmID. Фильтр возвращает кампании, связанные с товаром, и сам по себе не раскрывает их состав. Итоги многотоварной кампании относятся ко всей кампании. Для строки SKU брать товарную статистику. Кампании с чужими товарами или неподтверждённым составом исключать из анализа кампаний продавца. По нескольким своим SKU одну кампанию учитывать один раз по её внешнему ID.

## Какой инструмент вызвать

| Инструмент | Назначение и граница запроса |
|---|---|
| `list_shops` | Определить магазин ВБ. Его внешнее поле `id` служит значением `shop_id` на время работы. При неоднозначном выборе уточнить магазин у продавца. |
| `list_products` | По `vendor_code` (артикулы через запятую) и `visible=true` сверить nmID, прочитать текущие цены, СПП, статус витрины и настройки автоматизации товара. |
| `list_campaigns` | По массиву `product_id` найти связанные кампании. Поле `id` — внешний ID кампании ВБ. Здесь доступны её текущий статус, тип, ставки, бюджет и настройки. |
| `get_campaign_statistics` | По массиву проверенных ID кампаний получить расход, показы, клики и заказы за период по каждой кампании целиком. |
| `get_product_statistics` | По `vendor_code` и `visible=true` получить показатели выбранных товаров за период. Общий расход магазина в ответе имеет другой охват. |
| `get_shops_products_statistics_history` | По одному `product_id` посмотреть динамику товара с разбивкой по дням, неделям или месяцам. |
| `get_merged_prices` | Текущие или подённые цены и СПП по всему магазину, включая товары вне каталога XWAY. В схеме нет фильтра товаров. В общем кабинете этот метод пропустить. Текущую цену своего товара можно прочитать через `list_products`, для исторической нужна ограниченная выборка продавца. |
| `get_shops_products_campaigns_clusters` | По паре `product_id` и `campaign_id` получить кластеры, настройки и рекламную статистику кампании. Поля `*_jam` охватывают товар по запросам кластера. |
| `list_ab_tests` | По `product_wb_id` получить A/B-тесты главного фото, их состояние и расходы. Для сравнения изображений передать `include_image_stats=true`. |

## Ограничения по типам кампаний ВБ

Тип кампании взять из `list_campaigns`. В таблице указаны поля **кластера** из `get_shops_products_campaigns_clusters`. Статистику всей кампании возвращает отдельный метод `get_campaign_statistics`.

| Тип кампании | Ставка кластера `bid` и удержание позиции `automation.position_hold` | Исключение `excluded` и защита от автоисключения `fixed` |
|---|---|---|
| `MANUAL` — ручные ставки | Оба поля доступны. Без настроенного правила удержания `active=false`, а `target_place` и `max_bid` равны `null`. | Оба признака доступны. |
| `UNIFIED` — единая ставка | Оба поля равны `null`. | Оба признака доступны. |
| `CPC` — оплата за клик | Оба поля равны `null`. | Оба признака равны `null`. |

Для кластеров `CPC` ВБ не передаёт показы. Поля `views`, `ctr`, `ocr`, `view_to_cart_rate`, `cpm_fact` и `ocr_jam` всегда равны `null`. При сравнении типов кампаний эти показатели помечать как недоступные.

## Периоды, лимиты и чтение результатов

- Выполнять запросы последовательно, максимум пять в минуту с интервалом не менее 13 секунд. Страницы и повторные попытки входят в лимит. При HTTP 429 выдержать `Retry-After`, если он передан, и обычный минимальный интервал.
- Для статистики и исторических цен передавать вместе `date_from` и `date_to` в формате `YYYY-MM-DD`. Один период — до 366 дней включительно. Текущие настройки читать без дат. В списках передавать `pagination.next_offset` как следующий `offset` с теми же фильтрами до `null`.
- В `list_ab_tests` даты фильтруют `started_at` (запуск теста) по **UTC**, границы включительны. Можно указать только начало или только конец. Если обе границы опущены, в выдачу входят и тесты, которые ещё не запускались. Сумма `actual_expenses` у отобранных тестов показывает их фактические расходы. Для разбивки по дням списания нужны даты самих списаний. Для фильтра модели оплаты использовать `campaign_payment_type` со значениями `cpm` или `cpc`.
- В `list_campaigns` расписание `automation.schedule.slots` задано по **Europe/Moscow**. Слот `9` разрешает показы с 09:00 до 10:00 по Москве при активном расписании. При `active=false` сохранённые часы не ограничивают показы. Часовой пояс каждого другого временного поля сверять по описанию его метода.
- `null` означает отсутствие данных или невозможность расчёта. Сохранять различие между `null`, `0` и `false`. В статистике кампаний `orders` — заказанные единицы, `orders_count` — число заказов. Рекламные заказы и заказы Джема описывают пересекающиеся источники. Их сложение даёт двойной счёт, а выделить чистую органику одним полем Джема нельзя.
- Настроенный бюджет, лимит расхода и автопополнение читать отдельно. Фактический расход брать из статистики за выбранные даты. Дневной бюджет группового AI повторяется у участников и учитывается один раз на группу.
- `active` и `enabled` показывают состояние автоматизации на момент запроса. Фактические показы проверять за период. Дату изменения настройки устанавливать по журналу опытов или подтверждению продавца.

## Перед решением по рекламе

Выполнить `node scripts/rules.cjs preflight реклама-вб` (для Ozon — `реклама-озон`), сверить общее РЕК-34 через `node scripts/rules.cjs show РЕК-34`, затем `node scripts/opyt.cjs brief <код 1С>`. Статус, дату и замены проверять по действующему своду. [Правила](../ПРАВИЛА.md) · [Опыты](../ОПЫТ.md)

**ВБ.** Рекламу ведёт продавец. Агрессивный старт новых кампаний предусмотрен РЕК-34. При запрошенном разборе сопоставлять данные XWAY с прибылью, остатками, выкупом, конверсиями, ценой и историей опытов в Dashboard. ДРР рассчитывать в выкупе по формулам Dashboard. По РЕК-30 и РЕК-31 ассоциированные заказы могут включать чужие товары общего магазина. Сверять результат по фактическим заказам своей склейки. [Реклама ВБ](реклама-вб.md)

**Ozon.** По РЕК-34 каждый понедельник смотреть товары с остатком на Ozon, у которых за семь дней отсутствуют и расход XWAY, и списания «Оплаты за заказ». Предложение запуска готовить по шаблону Ozon. Для цели ДРР применять РЕК-32, для списаний — РЕК-23. Источники здесь — выгрузки, отчёты, скриншоты Ozon и снимок Dashboard.

Все изменения в кабинетах вносит продавец. Окончательную рекомендацию записывать в тот же ответ через `opyt.cjs change` с базой, датой проверки через семь дней и ссылкой на закономерность по ДАН-06 и ДАН-11. Для проверки закономерности менять один рычаг по ДАН-10. Результат сверять через `due` и фиксировать через `close`.
