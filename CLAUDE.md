# WB · РНП Дашборд — памятка для Claude

Читай этот файл в начале **любой** новой сессии в этом репозитории — он описывает
архитектуру, где что лежит и как безопасно продолжать работу без рисков всё
переделать заново. Пользовательские фичи и формулы — в `README.md`, здесь —
только то, что нужно ИИ-агенту для работы с кодовой базой.

## Что это

Управленческий дашборд Wildberries для продавца — один файл `index.html`
(вся вёрстка/стили/логика инлайн, без сборки), задеплоен на GitHub Pages
(`1malinin1.github.io/dashboard/`), ветка `claude/wb-dashboard-html-0kxavb`.
Пользователь общается по-русски, комментарии в коде — по-русски.

## Модель безопасности — САМОЕ ВАЖНОЕ

Реальные данные (каталог товаров, история заказов, финансы, реклама) хранятся
**зашифрованными** в `wb-secure.js` (AES-256-GCM, ключ — PBKDF2-SHA256 от
**кода доступа**). Это единственный файл с данными в репозитории — он публичный
(репозиторий публичный), поэтому шифрование — не формальность, а реальная защита.

- **Код доступа НИКОГДА не хранится в репозитории.** Его знает только
  пользователь и передаёт в чате. Если пользователь не дал код в начале
  сессии — **спроси**, не пытайся угадать и не бери из старых сообщений
  этого файла (тут его и не должно быть).
- Плейнтекст-версии данных (`wb-data.js`, `wb-reports.js`) **не коммитятся**
  (см. `.gitignore`) — они существуют только временно в `decrypted/`, которая
  тоже игнорируется гитом. Рабочая директория контейнера эфемерна: между
  сессиями `decrypted/` не переживёт — это ожидаемо, просто расшифруй заново.
- Единственное, что переживает переход в новую сессию, — то, что закоммичено
  в git. Поэтому: **закончил работу с данными → зашифровал → закоммитил
  wb-secure.js.** Не оставляй сессию с несинхронизированным decrypted/.
- Если пользователь просит сменить код доступа — расшифруй старым кодом,
  зашифруй новым, сообщи явно, что старый код перестанет работать у всех.

## Офлайн-скрипты (`scripts/`)

Перед первым запуском: `cd scripts && npm install` (нужен только пакет `xlsx`).

Типовой цикл обслуживания данных:

```
node scripts/decrypt.cjs <код>              # → decrypted/wb-data.js + wb-reports.js
# ...правите decrypted/ через один из скриптов ниже, или руками...
node scripts/encrypt.cjs <код>              # decrypted/*.js → wb-secure.js
git add wb-secure.js && git commit && git push
```

- **`decrypt.cjs <код>`** — расшифровывает `wb-secure.js` → `decrypted/wb-data.js` + `wb-reports.js`.
- **`encrypt.cjs <код>`** — обратно, `decrypted/*.js` → `wb-secure.js` (с самопроверкой roundtrip).
- **`ingest-finance.cjs файл1.xlsx файл2.xlsx ...`** — разбирает отчёты «О реализации» и/или
  «История затрат» (авто-определение типа), копит построчные записи в
  `decrypted/acc-finance.json` / `acc-ads.json` с дедупом по отпечатку строки
  (`rowHash`, идентичен воркеру на сайте). Можно вызывать много раз — накопитель
  не обнуляется. Требует уже расшифрованный `decrypted/wb-data.js` (список артикулов).
- **`bake-snapshot.cjs "новая подпись периода"`** — сливает накопитель в
  `decrypted/wb-reports.js`: новые даты перекрывают старые (без задвоения),
  остальные даты старого снимка сохраняются (недели складываются, не затираются).
  **Печатает контрольные суммы — сверяй их с личным кабинетом WB перед encrypt/push.**
- **`update-cost.cjs себестоимость.xlsx`** — обновляет `costPrice` в каталоге,
  печатает что заполнено впервые / что изменилось (новая поставка).
- **`missing-cost-report.cjs`** — генерит `decrypted/себестоимость-заполнить.xlsx`
  (товары без цены, сортировка по продажам) — отдать пользователю на заполнение.
- **`wb-extend-orders.cjs <день1.xlsx> …`** — продлевает `REAL_DATA.orderSeries` заказами ВБ из
  подённой аналитики (лист «Товары» → «Заказали товаров, шт», ключ «Артикул WB»; дата из «Общей
  информации»). Даты из файлов перезаписывают те же дни ряда, прочие сохраняются; ряды всех sku
  держатся одной длины с `dates`. Дальше `encrypt.cjs`.
- **`xlsx-xml-reader.cjs`** — резервный читатель .xlsx напрямую по XML (см. ниже,
  «когда SheetJS виснет»).
- **`lib/parse-wb.cjs`** — общая логика (num/rowHash/парсеры/агрегация). **Если
  меняешь формулу «Итого к оплате» или набор колонок в воркере `index.html` —
  обновляй и здесь**, иначе отпечатки строк расходятся и офлайн-дедуп сломается.

## Как передать пользователю недостающие товары / кастомные отчёты

Смотри `missing-cost-report.cjs` как образец: генерируешь `.xlsx` в `decrypted/`
через `XLSX.writeFile`, отдаёшь через инструмент отправки файлов пользователю
(SendUserFile или аналог в актуальном тулинге), просишь заполнить и прислать
обратно — дальше `update-cost.cjs` на результате.

## Ключевые данные/форматы (чтобы не удивляться при отладке)

- **`REAL_DATA.catalog[]`**: `{sku, factoryCode, supplierCode, name, category,
  wbStock, inTransitToWB, ownWarehouseStock, buyoutPct14d, containerQty,
  productionStatus, pending, costPrice}`. `costPrice: null` = себестоимость не задана
  (UI показывает предупреждение и позволяет вписать вручную/через файл).
- **`REAL_DATA.orderSeries`**: `{dates:[iso...], bySku:{sku:[qty по дням, той же длины что dates]}}`.
  Ряды должны быть строго одной длины с `dates` — при добавлении дней продлевай
  ВСЕ существующие ряды (нулями, если для sku заказов не было), иначе графики съедут.
- **`BAKED_FINANCE[]`** — свод по (дата+артикул): `{id,date,sku,name,category,
  qty,returnsQty,revenue,payout,logistics,penalty,storage,reimb,deduction,
  priyomka,loyalty,loyaltyPts}`. `revenue`/`qty`/`returnsQty` — только из строк
  Продажа/Возврат; остальные денежные поля — сырые суммы (логистика/хранение/
  штрафы и т.д. — расходы, не привязаны к конкретной продаже).
- **`BAKED_ADS[]`** — `{id,date,sku,spend}`, свод по (дата+артикул) из «Истории затрат»,
  только кампании `18+...`, артикул = последние цифры в названии кампании.
- **Формула «Итого к оплате»** (сверена на суммах всего магазина, точность 99.99%):
  `К перечислению − логистика − штрафы − удержания − хранение − операции приёмки
  − стоимость лояльности − баллы лояльности − возмещение издержек`.
  «Возмещение издержек» — это РАСХОД (вычитается), не доход. См. `finHoldings`/`finNet` в index.html.
- **Прибыль** = Итого к оплате − Себестоимость проданного − Реклама.
- WB отдаёт **два отчёта в неделю** — «по заказам» и «по выкупам» — их нужно
  оба грузить, они не пересекаются по отпечаткам строк и складываются.
- **Категория товара**: в финансовых отчётах WB поле «Предмет» может не совпадать
  с категорией каталога (напр. «Груши боксерские» в отчёте vs «Набор для бокса»
  в каталоге). Все таблицы/фильтры используют `normFinCategory()` — категорию
  каталога по SKU, а не то, что написано в отчёте. Не откатывай этот фикс.
- **Правило `hasActivity`**: товар попадает в таблицы по товарам (Главная/Финансы/
  Аналитика), только если были продажи, возвраты или реклама за период — иначе
  число товаров расходится между вкладками (это было багом, исправлено).

## Ozon — мультиплощадочность (в разработке, Фаза 1)

Дашборд расширяется на второй маркетплейс (Ozon) рядом с WB. Сделано на данный момент:

- **Модель данных**: `REAL_DATA.ozon = {catalog[], orderSeries:{dates[], byArt{}}, ordersMeta}`.
  Лежит в том же зашифрованном `wb-secure.js` (encrypt.cjs сериализует весь `REAL_DATA`).
  `ozon.catalog[]`: `{sku, name, category, wbSku}` — здесь **`sku` = артикул Озона**.
- **Связка ВБ↔Озон по арт. поставщика**: артикул Озона = `supplierCode` из WB-каталога
  (проверено: совпало 135/137). Отдельной таблицы соответствий НЕ нужно. В WB-каталоге
  `supplierCode` уникален (нужен для режима «Всего» — товары сливаются по нему).
- **Категория — единая (ВБ)**: у связанных товаров `ozon.catalog[].category` берётся из ВБ-каталога
  (Озон-«вид товара» не совпадает: ВБ«Пушкары»↔Озон«Каталка», расхождение 135/135). Так фильтр
  категорий одинаков на обеих площадках. Делается в `ozon-build.cjs`. Не откатывай — иначе фильтр
  «Пушкары» на Озоне обнуляет выборку.
- **Переключатель площадки** `#mpSwitch` (ВБ / Озон / Всего): глобальный `activeMp`,
  `applyMpData(mp)` «перенаводит» `RCAT/RSERIES/RDATES/RLAST` на выбранную площадку
  (для «Всего» — `combinedDataset()`, объединение по коду товара + сумма рядов на общей
  оси дат). Приём: у Озон-товаров `sku`=артикул, поэтому существующий код «Динамики»
  (оперирует `sku`) работает без переписывания.
- **`MP_TABS`** = список вкладок с поддержкой выбора площадки. **Сейчас `dynamics` + `turnover`.**
  На остальных вкладках `switchTab` принудительно ставит эффективную площадку «ВБ»
  (данные ВБ не ломаются), а переключатель скрыт (`OZDATA` есть → показан только на «Динамике»).
  Когда появятся финансы/реклама Озона — добавляй вкладки в `MP_TABS` и расширяй датасеты.
- **Заказы Озона по дням**: gross «Заказано» (все статусы, включая отмены — так решил
  пользователь; выкупы/процент выкупа — отдельная будущая механика). Денежные KPI/колонки
  на «Динамике» для Озона/Всего скрыты (нет данных воронки).
- **Нюанс покрытия дат**: заказы ВБ и Озона могут кончаться на разные даты (напр. ВБ по 14.07,
  Озон по 20.07). В «Всего» после более ранней даты суммарный ряд отражает только более
  свежую площадку — это честно помечается в шапке «Динамики» (не баг, а разное покрытие).

### Офлайн-инструменты Озона (`scripts/`)
- **`ozon-build.cjs <файл_Июль.xlsx> [остатки.xlsx] [дата]`** — собирает `REAL_DATA.ozon`
  (каталог из листа «Июль»: Артикул+Наименование+Вид товара; заказы из `decrypted/ozon-orders.json`;
  остатки из отчёта «Остатки», лист «Товары») и вписывает в `decrypted/wb-data.js`. Дальше `encrypt.cjs`.
- **Остатки Озона**: лист «Товары» отчёта «Остатки на складах». Колонки по индексу (шапка двухэтажная,
  данные с 5-й строки): 0 Артикул · 9 «Доступно к продаже» (→ `ozStock`) · 19 «В поставках в пути»
  (→ `ozTransit`) · 6 «Дней до конца остатка» · 7 «Среднесут. продажи 28д». `ozon.meta.stockDate` — дата снимка,
  `ozon.meta.buyoutAll` — общий % выкупа. Расчёт оборачиваемости Озона — ниже (`renderTurnoverOzon`).
- **`ozon-ingest-orders.cjs <файлы «Заказы»…>`** — разбирает отчёты Озона «Заказы» →
  `decrypted/ozon-orders.json` (`byDateArt/byDate/byDateNet/perArt/perArtNet/statuses`).
  Колонки: «Принят в обработку» (дата), «Артикул» (=арт.поставщика), «SKU» (озон), «Количество», «Статус».
  **Форматы дат РАЗНЫЕ по файлам**: csv — Д/М, xlsx — М/Д (определять пофайлово, иначе даты съедут).
  Дедуп по «Номер отправления + SKU» (не по дате). «Наши» — артикул ∈ supplierCode. Заказано = все
  статусы (gross); net = без «Отменён». Для окна выкупа нужен `byDateArtNet` (net по дата+артикул).
- **% выкупа (окно)** — считается в `ozon-build.cjs`: `net/gross` за **14 дней, заканчивающихся за 7 дней
  до последней даты** (HOLD=7, WIN=14). Последнюю неделю пропускаем — заказы ещё в пути («Доставляется»),
  выкуп не «дозрел» и завышается. По товару (при <10 заказов в окне — общий по магазину). Окно и общий %
  лежат в `ozon.meta.buyoutWindow`/`buyoutAll`; при малой истории (<8 дней) берётся весь период.
- **Простая оборачиваемость — ЕДИНАЯ для ВБ и Озона** (`simpleTurnList` + `renderTurnoverSimple`).
  Старую сложную ВБ-модель (`computeTurnover` с редакт. сроком/буфером/«Прибудет») **заменили** по просьбе
  пользователя (сам `computeTurnover`/`turnoverList`/`exportTurnoverCSV` остались в коде, но НЕ вызываются).
  Отличаются только источники полей: **ВБ** — `wbStock` · `pending.qty` (в пути, дату игнорируем) ·
  `buyoutPct14d` · `containerQty` · `productionStatus`(«На вывод»); **Озон** — `ozStock` · `ozTransit` ·
  `ozBuyout`, размер контейнера берётся из связанного ВБ-товара (кратность общая ВБ/Озон).
  Формула: ср.заказов **7 дн** × выкуп = продаж/день; **«хватит дней» = (остаток + в пути) ÷ продаж/день**
  (в пути складывается с остатком, показан акцентом: «354 **+1000 в пути**», «18 **→ 67**»).
  **Дозаказ** (`TURN_MIN_DAYS=130`, `TURN_COVER_DAYS=180`): если покрытия < 130 дн — партия = **6 мес продаж**
  = `ceil(продаж/день × 180)`, **округляется ВВЕРХ до контейнера** (текущий остаток НЕ вычитаем). «На вывод» —
  не дозаказываем (статус «На вывод»). Статус: ≥130 «Норма»; <130 «Пора дозаказать»; продажи есть, покрытия
  нет «Критично»; продаж нет «Нет продаж». Выкуп ВБ — 14-дневный из каталога; Озон — окно (см. выше).
  Колонки: Остаток(ВБ/Ozon) · Заказов/дн(7д) · %выкупа · Продаж/дн · Хватит,дн · Дозаказать(+конт.) · Статус.
  Селектор «Скорость» и старый CSV-дозаказ скрыты (фикс. окно 7 дн); режим «Всего» — подсказка выбрать площадку.
  Товары «На вывод» **полностью убраны** из таблицы и счётчиков (фильтр `status!=='discontinued'`).
  Фильтры: поиск · категории · **список товаров** (`#turnProduct`, мультивыбор конкретных sku) · статусы.
  Таблица компактная (влезает без прокрутки вбок): колонка одна «Товар / категория» (категория+sku 2-й строкой),
  меньше паддинги (`#turnTable`). `enhanceSelect` теперь читает `data-all`/`data-plural` (подпись «Все товары / N товаров»).

## UI-паттерны, которые уже есть — не изобретай заново

- **Кастомный `<select>`**: все выпадающие списки — не нативные `<select>`
  (те непредсказуемо открываются вверх/вниз и обрезаются `overflow:hidden`
  родителя). Компонент `enhanceSelect()` в конце `index.html` рендерит панель
  `position:fixed` под кнопкой; поддерживает мультивыбор (галочки) через
  `sel.multiple`. Категорийные фильтры — мультивыбор (`selCats(id)` +
  `catPred(cat)` — предикат, принимает строку или массив, `null` = без фильтра).
- **Sticky-шапка таблиц**: `.table-scroll{overflow:auto;max-height:74vh}` +
  `thead th{position:sticky;top:0}` — так и должно быть, не убирай max-height,
  иначе sticky снова перестанет работать (sticky требует свой scroll-контейнер).
- **Периоды**: везде недельно-месячная сетка (7/14/21/28 дн, 2–6 мес) — WB
  формирует отчёты раз в неделю, поэтому это осознанный выбор, не «забыли 30/90».
  На «Динамике заказов» вместо этого свободный календарь (`dynFrom`/`dynTo`) —
  там есть подённая история заказов, и это удобнее пресетов.
- **Тепловая заливка / мини-бары в ячейках** (`heatBg()`, `.share-fill`) —
  премиум-визуал таблиц; не заменяй на 3D/декоративный фон — обсуждали с
  пользователем и сознательно выбрали «данные как визуал» вместо буквального 3D.
- **Аврора-фон** (`body::before`, `@keyframes auroraDrift`) — фон-атмосфера,
  layering через `html{background:var(--page)}` + `body{background:transparent}`
  + `z-index:-1`. Если меняешь фон страницы — не потеряй это слоение.
- **Экран кода доступа** (`#lockScreen`, `initGate()`) — гейт перед рендером
  приложения. `bootApp()` вызывается только после успешной расшифровки.
  `hydrateData()` пересобирает производные каталога (`catalogCatBySku` и т.п.)
  после расшифровки — если добавляешь новую производную структуру от `RCAT`,
  регистрируй её пересборку там же, иначе после первой загрузки она не обновится.

## Тестирование (нет CI, тестируй руками через Playwright)

Песочница блокирует CDN, поэтому SheetJS с jsdelivr не грузится в headless-тестах
самого сайта — при необходимости используй `npm install xlsx` локально и
`page.route()` для подмены CDN-URL на локальный файл, либо тестируй те функции,
что не требуют XLSX-воркера (большинство логики).

Типовой прогон:
```
node http-server-эквивалент index.html-папку -p PORT
# в Playwright: page.goto → fill('#lockInput', код) → click('.lock-btn')
# → waitForFunction(() => FINANCE_CACHE.length > 0)
```
После правок в парсинге/агрегации — обязательно сверяй контрольные суммы
(выручка/к оплате/реклама) с тем, что видно в реальном личном кабинете WB —
пользователь их присылает или показывает на скриншотах.

## Стиль работы с пользователем

- Пользователь — не разработчик, объясняй результат человеческим языком,
  без жаргона, коротко «что сделал / что проверил / что дальше».
- Перед тем как заливать изменения в данные — прогоняй контрольные суммы и
  проговаривай их пользователю (он сверяет с личным кабинетом WB).
- Не удаляй/не переписывай историю git без явной просьбы (репозиторий публичный,
  но пользователь однажды отказался от чистки истории — уважай это).
- Мелкие правки (баги, визуал) можно и нужно делать в текущей сессии не спрашивая
  лишний раз; смену кода доступа, чистку git-истории, необратимые действия —
  подтверждать явно.
