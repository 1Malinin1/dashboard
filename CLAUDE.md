# WB · РНП Дашборд — памятка для Claude

Читай этот файл в начале **любой** новой сессии в этом репозитории — он описывает
архитектуру, где что лежит и как безопасно продолжать работу без рисков всё
переделать заново. Пользовательские фичи и формулы — в `README.md`, здесь —
только то, что нужно ИИ-агенту для работы с кодовой базой.

## Что это

Управленческий дашборд Wildberries для продавца — один файл `index.html`
(вся вёрстка/стили/логика инлайн, без сборки), задеплоен на GitHub Pages
(`1malinin1.github.io/dashboard/`), ветка `claude/wb-dashboard-html-0kxavb`.
Пользователь общается по-русски, комментарии в коде — по-русски.

## Модель безопасности — САМОЕ ВАЖНОЕ

Реальные данные (каталог товаров, история заказов, финансы, реклама) хранятся
**зашифрованными** в `wb-secure.js` (AES-256-GCM, ключ — PBKDF2-SHA256 от
**кода доступа**). Это единственный файл с данными в репозитории — он публичный
(репозиторий публичный), поэтому шифрование — не формальность, а реальная защита.

- **Код доступа НИКОГДА не хранится в репозитории.** Его знает только
  пользователь и передаёт в чате. Если пользователь не дал код в начале
  сессии — **спроси**, не пытайся угадать и не бери из старых сообщений
  этого файла (тут его и не должно быть).
- Плейнтекст-версии данных (`wb-data.js`, `wb-reports.js`) **не коммитятся**
  (см. `.gitignore`) — они существуют только временно в `decrypted/`, которая
  тоже игнорируется гитом. Рабочая директория контейнера эфемерна: между
  сессиями `decrypted/` не переживёт — это ожидаемо, просто расшифруй заново.
- Единственное, что переживает переход в новую сессию, — то, что закоммичено
  в git. Поэтому: **закончил работу с данными → зашифровал → закоммитил
  wb-secure.js.** Не оставляй сессию с несинхронизированным decrypted/.
- Если пользователь просит сменить код доступа — расшифруй старым кодом,
  зашифруй новым, сообщи явно, что старый код перестанет работать у всех.

## Офлайн-скрипты (`scripts/`)

Перед первым запуском: `cd scripts && npm install` (нужен только пакет `xlsx`).

Типовой цикл обслуживания данных:

```
node scripts/decrypt.cjs <код>              # → decrypted/wb-data.js + wb-reports.js
# ...правите decrypted/ через один из скриптов ниже, или руками...
node scripts/encrypt.cjs <код>              # decrypted/*.js → wb-secure.js
git add wb-secure.js && git commit && git push
```

- **`decrypt.cjs <код>`** — расшифровывает `wb-secure.js` → `decrypted/wb-data.js` + `wb-reports.js`.
- **`encrypt.cjs <код>`** — обратно, `decrypted/*.js` → `wb-secure.js` (с самопроверкой roundtrip).
- **`ingest-finance.cjs файл1.xlsx файл2.xlsx ...`** — разбирает отчёты «О реализации» и/или
  «История затрат» (авто-определение типа), копит построчные записи в
  `decrypted/acc-finance.json` / `acc-ads.json` с дедупом по отпечатку строки
  (`rowHash`, идентичен воркеру на сайте). Можно вызывать много раз — накопитель
  не обнуляется. Требует уже расшифрованный `decrypted/wb-data.js` (список артикулов).
- **`bake-snapshot.cjs "новая подпись периода"`** — сливает накопитель в
  `decrypted/wb-reports.js`: новые даты перекрывают старые (без задвоения),
  остальные даты старого снимка сохраняются (недели складываются, не затираются).
  **Печатает контрольные суммы — сверяй их с личным кабинетом WB перед encrypt/push.**
  **Переносит `BAKED_FUNNEL` из старого снимка как есть** (её печёт `bake-funnel.cjs`) —
  без этого пересборка молча стирала воронку и ломала вкладку «Товар». Отбрасывает
  полностью пустые агрегаты (ни штук, ни денег) — иначе нулевая строка со старой датой
  создавала фантомную дату и «история с …» съезжала на месяцы назад.
- **Строки без даты продажи** (прежде всего «Возмещение издержек»): WB не привязывает их
  к продаже — пусты ВСЕ колонки с датами. `aggregateFinanceRows` **размазывает** такие суммы
  по дням того же артикула пропорционально его выручке за день (остаток отдаётся последнему
  дню, чтобы сумма сошлась до копейки). Раньше они падали целиком на последний день периода
  и он проваливался на графике «Прибыль по дням» (26.07: 404 487 ₽ вместо ~792 000 ₽) —
  итог за период при этом был верным. Не возвращай `r.date || maxDate`.
- **`bake-funnel.cjs <день1.xlsx> …`** — запекает **воронку продаж** (детальный
  подённый отчёт WB «Воронка продаж») в `BAKED_FUNNEL` внутри `decrypted/wb-reports.js`.
  Источник — те же подённые файлы, что и `wb-extend-orders`/`ingest`, но берутся ВСЕ
  ступени: показы/переходы/корзина/заказы/выкуп + суммы + остатки. Колонки читаются
  **по имени** через `indexOf` (формат отчёта менялся — индексы «плывут»: в старом
  экспорте был лишний столбец «Артикул продавца» перед «Артикул WB», воркер в index.html
  до сих пор рассчитан на старый формат по фикс-индексам). Даты из файлов перекрывают те
  же дни снимка; печатает контрольные суммы. Дальше `encrypt.cjs`. Формат записи:
  `{id:дата_sku, date, sku, name, category, impressions, cardViews, addCart, addFav,
  ordersQty, buyoutQty, cancelQty, ordersSum, buyoutSum, cancelSum, wbStock, ownStock}`.
- **`update-cost.cjs себестоимость.xlsx`** — обновляет `costPrice` в каталоге,
  печатает что заполнено впервые / что изменилось (новая поставка).
- **`missing-cost-report.cjs`** — генерит `decrypted/себестоимость-заполнить.xlsx`
  (товары без цены, сортировка по продажам) — отдать пользователю на заполнение.
- **`wb-extend-orders.cjs <день1.xlsx> …`** — продлевает `REAL_DATA.orderSeries` заказами ВБ из
  подённой аналитики (лист «Товары» → «Заказали товаров, шт» кол.19, ключ «Артикул WB»; дата из «Общей
  информации»). Заодно копит **₽ по дням** в `orderSeries.money` (кол.31 «Заказали на сумму, ₽»,
  кол.34 «Выкупили на сумму, ₽»). Даты из файлов перезаписывают те же дни ряда, прочие сохраняются;
  ряды всех sku держатся одной длины с `dates`. Дальше `encrypt.cjs`.
- **`xlsx-xml-reader.cjs`** — резервный читатель .xlsx напрямую по XML (см. ниже,
  «когда SheetJS виснет»).
- **`lib/parse-wb.cjs`** — общая логика (num/rowHash/парсеры/агрегация). **Если
  меняешь формулу «Итого к оплате» или набор колонок в воркере `index.html` —
  обновляй и здесь**, иначе отпечатки строк расходятся и офлайн-дедуп сломается.

## Как передать пользователю недостающие товары / кастомные отчёты

Смотри `missing-cost-report.cjs` как образец: генерируешь `.xlsx` в `decrypted/`
через `XLSX.writeFile`, отдаёшь через инструмент отправки файлов пользователю
(SendUserFile или аналог в актуальном тулинге), просишь заполнить и прислать
обратно — дальше `update-cost.cjs` на результате.

## Ключевые данные/форматы (чтобы не удивляться при отладке)

- **`REAL_DATA.catalog[]`**: `{sku, factoryCode, supplierCode, name, category,
  wbStock, inTransitToWB, ownWarehouseStock, buyoutPct14d, containerQty,
  productionStatus, pending, costPrice}`. `costPrice: null` = себестоимость не задана
  (UI показывает предупреждение и позволяет вписать вручную/через файл).
- **`REAL_DATA.orderSeries`**: `{dates:[iso...], bySku:{sku:[qty по дням, той же длины что dates]}},
  money:{iso:{sku:[заказано₽,выкуплено₽]}}}`. Ряды `bySku` должны быть строго одной длины с `dates` —
  при добавлении дней продлевай ВСЕ существующие ряды (нулями, если для sku заказов не было), иначе
  графики съедут. `money` — разреженная карта по дням (не по индексам), питает график «Сумма заказов
  и выкупа по дням» (₽) на «Динамике». Аналогично у Озона: `ozon.orderSeries.money` (см. ниже).
  В UI карту отдаёт MP-aware хелпер `mpMoney()`; на «Всего» деньги не суммируются (площадки раздельно).
- **`BAKED_FINANCE[]`** — свод по (дата+артикул): `{id,date,sku,name,category,
  qty,returnsQty,revenue,payout,logistics,penalty,storage,reimb,deduction,
  priyomka,loyalty,loyaltyPts}`. `revenue`/`qty`/`returnsQty` — только из строк
  Продажа/Возврат; остальные денежные поля — сырые суммы (логистика/хранение/
  штрафы и т.д. — расходы, не привязаны к конкретной продаже).
- **`BAKED_ADS[]`** — `{id,date,sku,spend}`, свод по (дата+артикул) из «Истории затрат»,
  только кампании `18+...`, артикул = последние цифры в названии кампании.
- **`BAKED_FUNNEL[]`** — зашитая воронка по (дата+sku): `{id,date,sku,name,category,
  impressions,cardViews,addCart,addFav,ordersQty,buyoutQty,cancelQty,ordersSum,buyoutSum,
  cancelSum,wbStock,ownStock}`. Питает вкладку «Товар» (разбор воронки). Живёт в
  `wb-reports.js` рядом с `BAKED_FINANCE`/`BAKED_ADS`; `encrypt/decrypt.cjs` его переносят
  (с обратной совместимостью: старый снимок без воронки → `[]`). В UI `fdbRefreshCache`
  кладёт `BAKED_FUNNEL` базовым слоем, браузерные загрузки IndexedDB — поверх (даты
  загрузок перекрывают). `funnelIsBaked`/`funnelHasBaked` — как у финансов.
  **Суммы `ordersSum`/`buyoutSum` воронки сходятся с `orderSeries.money` до рубля** (один
  источник — подённые файлы), это хороший чек консистентности.
- **Формула «Итого к оплате»** (сверена на суммах всего магазина, точность 99.99%):
  `К перечислению − логистика − штрафы − удержания − хранение − операции приёмки
  − стоимость лояльности − баллы лояльности − возмещение издержек`.
  «Возмещение издержек» — это РАСХОД (вычитается), не доход. См. `finHoldings`/`finNet` в index.html.
- **Прибыль** = Итого к оплате − Себестоимость проданного − Реклама.
- **Главная vs Финансы — разные вкладки, не дубль**: «Главная» = ПРИБЫЛЬ (выручка − удержания WB
  − себестоимость − реклама, маржа). «Финансы» = СВЕРКА С WB: «сколько придёт на счёт и за что
  удержано» — герой-KPI «Итого к оплате», разложение `выручка = комиссия(revenue−payout) + логистика
  + хранение/приёмка + штрафы/удержания + возмещение + итого к оплате` (карточка «Куда уходит выручка»),
  по товарам все удержания раздельно + **% каждого раздела от выручки товара** (доля «съедания») и колонка
  «Забирает WB» (сумма+% всех удержаний). Себестоимости/рекламы на «Финансах» НЕТ (WB про них не знает).
- **Вкладка «Инструкция» удалена** (была под браузерную загрузку, теперь данные — через диалог).
  `TABS` = home/dynamics/turnover/product/finance/analytics. CSS-классы `.guide-*` остались, но не
  используются (мёртвые) — не восстанавливай вкладку без явной просьбы.
- WB отдаёт **два отчёта в неделю** — «по заказам» и «по выкупам» — их нужно
  оба грузить, они не пересекаются по отпечаткам строк и складываются.
- **Категория товара**: в финансовых отчётах WB поле «Предмет» может не совпадать
  с категорией каталога (напр. «Груши боксерские» в отчёте vs «Набор для бокса»
  в каталоге). Все таблицы/фильтры используют `normFinCategory()` — категорию
  каталога по SKU, а не то, что написано в отчёте. Не откатывай этот фикс.
- **Правило `hasActivity`**: товар попадает в таблицы по товарам (Главная/Финансы/
  Аналитика), только если были продажи, возвраты или реклама за период — иначе
  число товаров расходится между вкладками (это было багом, исправлено).
- **Доп. аналитические блоки по вкладкам** (карточки-разрезы, дополняют основные таблицы):
  Главная — «Что двигает прибыль» (`renderProfitDrivers`: топ-3 в плюсе / топ-3 в минусе под KPI),
  «Прибыль по дням» (`profitDayChart`: прибыль на своей шкале — столбцы зелёный+/красный−, плюс
  накопительная линия; ноль линии совмещён с нулём столбцов; конец линии = итог периода = KPI прибыли)
  и «Разбивка прибыли по категориям» (`renderHomeCatProfit`, бары +/−); Товар —
  «Топ узких мест по всем товарам» (`renderBottlenecks`: где товар конвертит хуже среднего
  по магазину; потери пересчитаны в **заказы** через средние конверсии; только `impressions>=300`);
  Аналитика — «Разбор возвратов» (`renderReturns`) и «Цена безубыточности» (`renderBreakeven`);
  Финансы — «Логистика и хранение по категориям» (`renderFinLogByCat`). Таблицы возвратов и
  безубыточности **сортируемые** (`anRetSortState`/`anBeSortState` + `wireSortable`).
- **Цена безубыточности** (`renderBreakeven`) = юнит-экономика: `(себестоимость + логистика/ед) ÷
  (1 − доля комиссии WB от цены)`. **Реклама, хранение, штрафы НЕ включаются** — это расходы периода,
  деление их на штуки завышало безубыток у малотиражных товаров (была цифра 8000₽ у товара за 1400₽).
  Не возвращай `finHoldings(r)` в формулу — это осознанный выбор ради адекватных цифр.

## Загрузка данных — только через диалог (браузерные дропзоны убраны)

Пользователь грузит все данные **через диалог** (ИИ запекает в снимок), а не через
браузер. Дропзоны на вкладках «Товар» (себестоимость, воронка) и «Финансы» (реализация,
реклама) **удалены** — браузерная загрузка жила только в IndexedDB локально до чистки
кэша и вводила в заблуждение. Функции-обработчики `handleFunnelFiles`/`handleCostFiles`/
`handleFinanceFiles`/`handleAdsFiles` и воркер парсинга **остались в коде, но НЕ
подключены к UI** (мёртвый код) — если понадобится снова, достаточно вернуть дропзону и
обвязку. `renderCostInfo`/`renderAdsHistoryInfo` — с null-guard, безопасны без своих
элементов. **Разные цифры в разных браузерах** = в одном остались локальные данные
(старые IndexedDB-загрузки финансов/рекламы/воронки или ручные правки себестоимости
`costOverrides` в localStorage `wb_cost_overrides_v1`). В строке свежести показывается
ссылка «сбросить локальные данные» (`localDataResetLink()` → `resetLocalData()`: чистит
три стора IndexedDB + costOverrides + reload) — только когда локальные данные есть
(флаги `*HasBaked && !*IsBaked`). После сброса везде — единый зашитый снимок.
**Воронка теперь запекается в снимок** — см. `BAKED_FUNNEL` ниже
(`FUNNEL_CACHE` = зашитый снимок + браузерные загрузки поверх, как у финансов).

## Вкладка «Товар» — разбор воронки (`renderProductPeriods` и др.)

Блок «Разбор воронки»: область `prodScope` (`sku`/`cat`/`all` — сегмент `#prodScopeSeg`),
выбор товара/категории, два периода A/B. `prodScopeSkus()` даёт набор sku (null = все);
`aggregateFunnel(skuSet,from,to)` сводит воронку по набору (остаток = последняя дата в
периоде у каждого sku, суммарно). Три вывода:
- **Визуальная воронка** (`renderFunnelVis`, `FUNNEL_STAGES` = Показы→Переходы→Корзина→
  Заказы→Выкуп): полосы шириной «доля от показов», конвертеры между ступенями (`connectorConv`)
  с Δ п.п. к периоду B; шаг с наибольшей просадкой помечается «узкое место» (`weakStepIndex`).
- **Авто-диагностика** (`renderFunnelDiag`, `weakestDeclineIndex`): сквозная конверсия +
  самый просевший и самый выросший шаг vs B (п.п.). Без B — подсказка заполнить B.
- **График по дням** (`renderProdChart`, `CHART_METRICS`, `funnelDailyAgg`, `metricBars`):
  выбранная метрика (заказы/₽/CTR/конверсия/%выкупа) по всем дням воронки.
Ниже — полная таблица метрик A/B (`FUNNEL_METRICS`). Всё показывается только когда есть
`FUNNEL_CACHE` и область «готова» (`prodScopeReady`: для `sku` — выбран товар). Перерисовка —
`refreshProductView()` (на смене области/товара/периода и на входе во вкладку).

## Ozon — мультиплощадочность (в разработке, Фаза 1)

Дашборд расширяется на второй маркетплейс (Ozon) рядом с WB. Сделано на данный момент:

- **Модель данных**: `REAL_DATA.ozon = {catalog[], orderSeries:{dates[], byArt{}, money{}}, funnel[], ordersMeta}`.
  `ozon.funnel[]` — воронка Озона (см. `ozon-funnel-build.cjs`), питает вкладку «Товар» на площадке Озон.
  `ozon.catalog[].ozonSku` — числовой SKU Озона (из отчёта воронки, кол. «SKU»), нужен для прямой
  ссылки на карточку `ozon.ru/product/{ozonSku}/`; проставляет `ozon-funnel-build.cjs`.
- **Кликабельные артикулы**: `skuLink(sku)`/`productUrl(sku)` — артикул в таблицах ведёт на карточку
  товара: ВБ → `wildberries.ru/catalog/{sku}/detail.aspx`; Озон → `ozon.ru/product/{ozonSku}/` (или
  поиск по артикулу, если числового SKU нет); «Всего» — без ссылки. Площадка берётся из `_appliedMp`.
  `ozon.orderSeries.money` = `{iso:{арт:[заказано₽,выкуплено₽]}}` (заказано = «Ваша цена» всех строк,
  выкуплено = строки со статусом «Доставлен»; собирается в `ozon-build.cjs` из `byDateArtRub/byDateArtBuyRub`).
  Лежит в том же зашифрованном `wb-secure.js` (encrypt.cjs сериализует весь `REAL_DATA`).
  `ozon.catalog[]`: `{sku, name, category, wbSku}` — здесь **`sku` = артикул Озона**.
- **Связка ВБ↔Озон по арт. поставщика**: артикул Озона = `supplierCode` из WB-каталога
  (проверено: совпало 135/137). Отдельной таблицы соответствий НЕ нужно. В WB-каталоге
  `supplierCode` уникален (нужен для режима «Всего» — товары сливаются по нему).
- **Категория — единая (ВБ)**: у связанных товаров `ozon.catalog[].category` берётся из ВБ-каталога
  (Озон-«вид товара» не совпадает: ВБ«Пушкары»↔Озон«Каталка», расхождение 135/135). Так фильтр
  категорий одинаков на обеих площадках. Делается в `ozon-build.cjs`. Не откатывай — иначе фильтр
  «Пушкары» на Озоне обнуляет выборку.
- **Переключатель площадки** `#mpSwitch` (ВБ / Озон / Всего): глобальный `activeMp`,
  `applyMpData(mp)` «перенаводит» `RCAT/RSERIES/RDATES/RLAST` на выбранную площадку
  (для «Всего» — `combinedDataset()`, объединение по коду товара + сумма рядов на общей
  оси дат). Приём: у Озон-товаров `sku`=артикул, поэтому существующий код «Динамики»
  (оперирует `sku`) работает без переписывания.
- **Воронка Озона (вкладка «Товар»)**: `REAL_DATA.ozon.funnel` (записи как FUNNEL_CACHE, sku=арт.продавца).
  Товар-таб теперь MP-aware: `activeFunnel()` отдаёт `FUNNEL_CACHE` (ВБ) или `OZ_FUNNEL` (Озон, из снимка),
  для «Всего» — пусто + подсказка «смотрите по площадке». Все функции воронки (`funnelDates`,
  `aggregateFunnel`, `funnelDailyAgg`) ходят через `activeFunnel()`. Последняя ступень: у Озона «Доставлено»
  (`stLabel()`), у ВБ «Выкуп». При смене площадки `applyMpData` сбрасывает `selectedSku`/`_prodPeriodsMp`
  (выбор товара и даты — свои на каждой площадке). `buyoutSum` у Озона отчёт не отдаёт → **ОЦЕНКА**
  (доставлено × средний чек `ordersSum/ordersQty`), в графике помечается «≈ оценка». В таблице метрик
  на Озоне свои подписи (Доставлено/Доля доставки) и скрыты поля, которых нет (addFav/cancelSum/остатки WB).
- **`MP_TABS`** = список вкладок с поддержкой выбора площадки. **Сейчас `dynamics` + `turnover` + `product`.**
  На остальных вкладках `switchTab` принудительно ставит эффективную площадку «ВБ»
  (данные ВБ не ломаются), а переключатель скрыт (`OZDATA` есть → показан только на «Динамике»).
  Когда появятся финансы/реклама Озона — добавляй вкладки в `MP_TABS` и расширяй датасеты.
- **Заказы Озона по дням**: gross «Заказано» (все статусы, включая отмены — так решил
  пользователь; выкупы/процент выкупа — отдельная будущая механика). Денежные KPI/колонки
  на «Динамике» для Озона/Всего скрыты (нет данных воронки).
- **Нюанс покрытия дат**: заказы ВБ и Озона могут кончаться на разные даты (напр. ВБ по 14.07,
  Озон по 20.07). В «Всего» после более ранней даты суммарный ряд отражает только более
  свежую площадку — это честно помечается в шапке «Динамики» (не баг, а разное покрытие).

### Офлайн-инструменты Озона (`scripts/`)
- **`ozon-build.cjs <файл_Июль.xlsx> [остатки.xlsx] [дата]`** — собирает `REAL_DATA.ozon`
  (каталог из листа «Июль»: Артикул+Наименование+Вид товара; заказы из `decrypted/ozon-orders.json`;
  остатки из отчёта «Остатки», лист «Товары») и вписывает в `decrypted/wb-data.js`. Дальше `encrypt.cjs`.
- **Остатки Озона**: лист «Товары» отчёта «Остатки на складах» (двухэтажная шапка, данные с 5-й строки).
  Колонки ищутся **по имени** (индексы плывут между версиями), с фолбэком на индексы:
  0 Артикул · «Доступно к продаже» (→ `ozStock`) · 6 «Дней до конца остатка» · 7 «Среднесут. продажи 28д».
  **`ozTransit` = «В заявках на поставку» + «В поставках в пути»** — это две непересекающиеся стадии
  под общей шапкой «В пути на склад Ozon»: заявка создана / партия физически едет. Продавец считает
  созданную заявку уже «направленным на Озон» товаром, поэтому суммируем. НЕ путать с `ozIncoming`. `ozon.meta.stockDate` — дата снимка,
  `ozon.meta.buyoutAll` — общий % выкупа. Расчёт оборачиваемости Озона — ниже (`renderTurnoverOzon`).
- **`ozon-funnel-build.cjs <отчёт.xlsx>`** — запекает **воронку Озона** в `REAL_DATA.ozon.funnel`.
  Источник — отчёт «Аналитика → По товарам, подённо» (лист «По товарам», многоуровневая шапка,
  секция «Воронка продаж»). Колонки по имени (в под-строке шапки): «Показы всего»→impressions,
  «Посещения карточки»→cardViews, «Добавления в корзину всего»→addCart, «Заказано товаров»→ordersQty,
  «Доставлено товаров»→**buyoutQty** (аналог «Выкупили» ВБ — «доставлено=получил», дозревает),
  «Отменено товаров»→cancelQty, «Заказано на сумму»→ordersSum. Ключ — «Артикул продавца» (=supplierCode);
  берём только наши (∈ supplierCode ВБ). **Формат чисел Озона: запятая=разделитель тысяч, точка=десятичная.**
  Записи — та же форма, что FUNNEL_CACHE. `buyoutSum` не даётся отчётом (=0). Дальше `encrypt.cjs`.
  В UI воронку Озона отдаёт `activeFunnel()` (см. ниже), последняя ступень подписана «Доставлено».
- **`ozon-ingest-orders.cjs <файлы «Заказы»…>`** — разбирает отчёты Озона «Заказы» →
  `decrypted/ozon-orders.json` (`byDateArt/byDate/byDateNet/perArt/perArtNet/statuses`).
  Колонки: «Принят в обработку» (дата), «Артикул» (=арт.поставщика), «SKU» (озон), «Количество», «Статус».
  **Форматы дат РАЗНЫЕ по файлам**: csv — Д/М, xlsx — М/Д (определять пофайлово, иначе даты съедут).
  Дедуп по «Номер отправления + SKU» (не по дате). «Наши» — артикул ∈ supplierCode. Заказано = все
  статусы (gross); net = без «Отменён». Для окна выкупа нужен `byDateArtNet` (net по дата+артикул).
- **% выкупа (окно)** — считается в `ozon-build.cjs`: `net/gross` за **14 дней, заканчивающихся за 7 дней
  до последней даты** (HOLD=7, WIN=14). Последнюю неделю пропускаем — заказы ещё в пути («Доставляется»),
  выкуп не «дозрел» и завышается. По товару (при <10 заказов в окне — общий по магазину). Окно и общий %
  лежат в `ozon.meta.buyoutWindow`/`buyoutAll`; при малой истории (<8 дней) берётся весь период.
- **Простая оборачиваемость — ЕДИНАЯ для ВБ и Озона** (`simpleTurnList` + `renderTurnoverSimple`).
  Старую сложную ВБ-модель (`computeTurnover` с редакт. сроком/буфером/«Прибудет») **заменили** по просьбе
  пользователя (сам `computeTurnover`/`turnoverList`/`exportTurnoverCSV` остались в коде, но НЕ вызываются).
  Отличаются только источники полей: **ВБ** — `wbStock` · `pending.qty` (в пути, дату игнорируем) ·
  `buyoutPct14d` · `containerQty` · `productionStatus`(«На вывод»); **Озон** — `ozStock` · `ozTransit` ·
  `ozBuyout`, размер контейнера берётся из связанного ВБ-товара (кратность общая ВБ/Озон).
  Формула: ср.заказов **7 дн** × выкуп = продаж/день; **«хватит дней» = (остаток + в пути) ÷ продаж/день**
  (в пути складывается с остатком, показан акцентом: «354 **+1000 в пути**», «18 **→ 67**»).
- **«В пути» — точные данные по площадкам** (приоритетный источник, признак — `RD.meta.transitDate`):
  рабочий файл продавца «на оптовых» (вкладки `вб` / `озон` / `в пути` / `в пути 2`), скрипт
  **`update-transit.cjs`**. Формула: **ВБ** = `вб.Итог` + `в пути.Кол-во вб` + `в пути 2.кол-во вб`;
  **Озон** = `озон.Итог` + `в пути.Кол-во озон` + `в пути 2.кол-во озон`. Вкладки `вб`/`озон` — товар на
  своих складах, который «должно уехать» на площадку; `в пути`/`в пути 2` — едущие партии. Ключ везде —
  **арт. поставщика** (= WB `supplierCode` = Озон `sku`); в «в пути 2» колонки названы иначе
  (`арт`/`кол-во вб`/`кол-во озон`, порядок обратный) — ищем по имени. Пишется: ВБ → `catalog[].pending.qty`,
  Озон → `ozon.catalog[].ozIncoming`. **`ozIncoming` ≠ `ozTransit`**: `ozTransit` — то, что Озон сам
  показывает по созданным поставкам (из отчёта остатков), `ozIncoming` — наши данные (свои склады +
  едущие партии). Они **складываются**, не заменяют друг друга; в UI это строка «**+N ожидается**»
  рядом с «+N в пути». Файл — полный список едущего, поэтому старое `pending` перед заливкой **очищается**.
- **Фолбэк `OZ_RESERVE_SHARE=0.35`** (когда точных данных нет): «в пути» ВБ = вся заказанная партия, но доля 35%
  предназначена Озону (лежит на СВОЁМ складе продавца, ещё не едет на Озон → в отчёте остатков Озона
  её нет). Поэтому в `simpleTurnList`: у **ВБ** «в пути» = `pending.qty×0.65` (везде — таблица, «хватит»,
  дозаказ, CSV), а **Озон** получает `pending.qty связанного ВБ ×0.35` как поле `ozReserve` — отдельная
  строка «**+N со склада**» в ячейке остатка (НЕ путать с `ozTransit` = реальная поставка на Озон из отчёта),
  входит в `covered` (хватит/дозаказ). В CSV Озона — доп. колонка «Со склада (резерв Озон)».
  **Дозаказ** (`TURN_MIN_DAYS=130`, `TURN_COVER_DAYS=180`): если покрытия < 130 дн — партия = **6 мес продаж**
  = `ceil(продаж/день × 180)`, **округляется ВВЕРХ до контейнера** (текущий остаток НЕ вычитаем). «На вывод» —
  не дозаказываем (статус «На вывод»). Статус: ≥130 «Норма»; <130 «Пора дозаказать»; продажи есть, покрытия
  нет «Критично»; продаж нет «Нет продаж». Выкуп ВБ — 14-дневный из каталога; Озон — окно (см. выше).
  Колонки: Остаток(ВБ/Ozon) · Заказов/дн(7д) · %выкупа · Продаж/дн · Хватит,дн · Дозаказать(+конт.) · Заказать(через N дн) · Статус.
  Селектор «Скорость» скрыт (фикс. окно 7 дн); режим «Всего» — подсказка выбрать площадку.
  Товары «На вывод» **полностью убраны** из таблицы и счётчиков (фильтр `status!=='discontinued'`).
  Фильтры: поиск · категории · **список товаров** (`#turnProduct`, мультивыбор конкретных sku).
  Таблица компактная (влезает без прокрутки вбок): колонка одна «Товар / категория» (категория+sku 2-й строкой),
  меньше паддинги (`#turnTable`). `enhanceSelect` теперь читает `data-all`/`data-plural` (подпись «Все товары / N товаров»).
- **Вид «По месяцам»** на «Оборачиваемости» (сегмент `#turnViewSeg`, состояние `turnView`):
  история заказов *артикул × месяц* (`monthlyOrders` + `renderTurnMonths`). Зачем: фиксированное
  окно 7 дн врёт — у новинок в старых месяцах нули, а ноль у товара в ауте не значит «не покупают».
  Продавец смотрит пики и решает дозаказ сам. Пиковый месяц подсвечен акцентом, заливка — внутри
  товара, «Ср/мес» считается **только по месяцам с продажами** (иначе новинки занижены), неполные
  месяцы помечены `*`. **Выкуп здесь фиксированный `TURN_PEAK_BUYOUT=0.85`** (по просьбе продавца;
  свой % выкупа на истории с нулями не показателен) — из него колонка «Продаж/дн в пик».
  Суммы ₽ в этом виде НЕ показываем: деньги в `orderSeries.money` есть только с середины июля,
  на истории они не сходятся. Экспорт CSV переключается вместе с видом (`exportTurnMonthsCSV`).
- **Фильтры по колонкам (Excel-стиль)** — у каждой числовой/статусной колонки в шапке кнопка-воронка
  (`.col-filter`, `thSortF()`): клик открывает панель `.colfilter-panel` (переиспользует стили `.uisel-panel`)
  со списком **значений этой колонки** (с подсчётом строк и поиском при >12 значений). Отметил — таблица
  показывает только эти значения; **фильтры комбинируются логическим И** и стакаются по колонкам (выбрал статус
  «Пора дозаказать», затем в «Дозаказать» — конкретные партии). Состояние — `turnColFilters{ключ:Set значений}`
  (пусто = без фильтра), логика — `turnColDefs()` (`val(r)`=каноничное значение колонки, `sortVal(v)`=для сортировки
  списка), отбор — `turnFilteredRows(all,exceptKey)` (панель + все колоночные фильтры; `exceptKey` даёт «контекстные»
  списки как в Excel). Панель = отдельный `position:fixed` div в `<body>` (не режется `overflow` таблицы),
  один за раз (`_colFilterKey`), закрывается по клику вне/Esc/скроллу. Клик по воронке не сортирует
  (`wireSortable` пропускает `.col-filter`). **Старый тулбар-селект статусов удалён** — статус теперь колоночный
  фильтр (мультивыбор, лучше). Работает одинаково для ВБ и Озона; при смене площадки `applyMpData` сбрасывает
  `turnColFilters`. **Экспорт CSV (`exportTurnoverCSV`) идёт строго по текущим фильтрам+сортировке** (что видишь —
  то и качаешь), все колонки + ИТОГО по дозаказу; кнопка «Скачать таблицу CSV».

## UI-паттерны, которые уже есть — не изобретай заново

- **Кастомный `<select>`**: все выпадающие списки — не нативные `<select>`
  (те непредсказуемо открываются вверх/вниз и обрезаются `overflow:hidden`
  родителя). Компонент `enhanceSelect()` в конце `index.html` рендерит панель
  `position:fixed` под кнопкой; поддерживает мультивыбор (галочки) через
  `sel.multiple`. Категорийные фильтры — мультивыбор (`selCats(id)` +
  `catPred(cat)` — предикат, принимает строку или массив, `null` = без фильтра).
- **Sticky-шапка таблиц**: `.table-scroll{overflow:auto;max-height:74vh}` +
  `thead th{position:sticky;top:0}` — так и должно быть, не убирай max-height,
  иначе sticky снова перестанет работать (sticky требует свой scroll-контейнер).
- **«Динамика заказов» → таблица «Товары за период»** имеет два вида (сегмент `#dynViewSeg`, состояние
  `dynView`): **«По дням»** (по умолчанию) — сводка *товар × дни* (`renderDynPivot`), как в рабочем файле
  продавца: колонка на каждый день периода, заливка `heatBg` показывает динамику **внутри товара**
  (относительно его же лучшего дня), закреплённая строка «Всего по дням» даёт итог по магазину за каждый
  день, «Итого» залипает справа (`position:sticky;right:0`), понедельники помечены пунктиром (`.wk`).
  Горизонтальная прокрутка тут НОРМАЛЬНА (в отличие от «Оборачиваемости») — колонок столько, сколько дней;
  товар и «Итого» залипают, поэтому не теряются. **«Свод»** — прежняя таблица (товар/категория/шт/доля/₽).
  Денежные колонки показываются, когда для площадки есть `orderSeries.money` (у «Всего» — скрыты).
- **Периоды**: везде недельно-месячная сетка (7/14/21/28 дн, 2–6 мес) — WB
  формирует отчёты раз в неделю, поэтому это осознанный выбор, не «забыли 30/90».
  На «Динамике заказов» вместо этого свободный календарь (`dynFrom`/`dynTo`) —
  там есть подённая история заказов, и это удобнее пресетов.
- **Тепловая заливка / мини-бары в ячейках** (`heatBg()`, `.share-fill`) —
  премиум-визуал таблиц; не заменяй на 3D/декоративный фон — обсуждали с
  пользователем и сознательно выбрали «данные как визуал» вместо буквального 3D.
- **Аврора-фон** (`body::before`, `@keyframes auroraDrift`) — фон-атмосфера,
  layering через `html{background:var(--page)}` + `body{background:transparent}`
  + `z-index:-1`. Если меняешь фон страницы — не потеряй это слоение.
- **Экран кода доступа** (`#lockScreen`, `initGate()`) — гейт перед рендером
  приложения. `bootApp()` вызывается только после успешной расшифровки.
  `hydrateData()` пересобирает производные каталога (`catalogCatBySku` и т.п.)
  после расшифровки — если добавляешь новую производную структуру от `RCAT`,
  регистрируй её пересборку там же, иначе после первой загрузки она не обновится.

## Тестирование (нет CI, тестируй руками через Playwright)

Песочница блокирует CDN, поэтому SheetJS с jsdelivr не грузится в headless-тестах
самого сайта — при необходимости используй `npm install xlsx` локально и
`page.route()` для подмены CDN-URL на локальный файл, либо тестируй те функции,
что не требуют XLSX-воркера (большинство логики).

Типовой прогон:
```
node http-server-эквивалент index.html-папку -p PORT
# в Playwright: page.goto → fill('#lockInput', код) → click('.lock-btn')
# → waitForFunction(() => FINANCE_CACHE.length > 0)
```
После правок в парсинге/агрегации — обязательно сверяй контрольные суммы
(выручка/к оплате/реклама) с тем, что видно в реальном личном кабинете WB —
пользователь их присылает или показывает на скриншотах.

## Стиль работы с пользователем

- Пользователь — не разработчик, объясняй результат человеческим языком,
  без жаргона, коротко «что сделал / что проверил / что дальше».
- Перед тем как заливать изменения в данные — прогоняй контрольные суммы и
  проговаривай их пользователю (он сверяет с личным кабинетом WB).
- Не удаляй/не переписывай историю git без явной просьбы (репозиторий публичный,
  но пользователь однажды отказался от чистки истории — уважай это).
- Мелкие правки (баги, визуал) можно и нужно делать в текущей сессии не спрашивая
  лишний раз; смену кода доступа, чистку git-истории, необратимые действия —
  подтверждать явно.
